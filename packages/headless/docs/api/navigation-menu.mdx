# navigationMenu

Creates the navigation menu parts in one call: the bar root, its list of items, the viewport-shared panels, and the moving indicator. The closure owns the open-value store; a value-carrying trigger announces its clicks, the root mirrors the announcement into the store, and the matching panel portals into the shared viewport.

## Basic Usage

```tsx
import { signal } from "@hellajs/core";
import { mount } from "@hellajs/dom";
import { navigationMenu } from "@hellajs/headless";

const value = signal("");

const Nav = navigationMenu({
  value: () => value(),
  onValueChange: (next) => value(next),
});

mount(
  <Nav.Root>
    <Nav.List>
      <Nav.Item>
        <Nav.Trigger value="learn">Learn</Nav.Trigger>
        <Nav.Content value="learn">
          <Nav.Link href="#learn">Intro</Nav.Link>
        </Nav.Content>
      </Nav.Item>
      <Nav.Item>
        <Nav.Trigger value="reference">Reference</Nav.Trigger>
        <Nav.Content value="reference">
          <Nav.Link href="#reference">API</Nav.Link>
        </Nav.Content>
      </Nav.Item>
    </Nav.List>
    <Nav.Indicator />
  </Nav.Root>,
  "#app",
);
// Clicking a trigger opens its panel in the shared viewport; clicking
// another trigger swaps the panel, clicking the open trigger closes
// the bar, and the indicator slides under the active trigger.
```

## API

```typescript
function navigationMenu(options?: NavigationMenuOptions): NavigationMenuParts
```

- `options.value`: Controlled id of the open panel (`""` when closed). When given, the factory never writes its internal signal and `onValueChange` reports the requested value.
- `options.onValueChange`: Called with every store write mirrored from a trigger announcement.
- `options.viewport`: Whether the root renders the shared viewport slot as its last child. Default `true`; set `false` to compose a `Viewport` manually.
- **Returns**: The part set, composed as `Nav.Root`-style members.

### Parts

| Part | Renders |
|---|---|
| `Root` | The bar root (`data-slot="navigation-menu"`) that mirrors trigger announcements into the store and appends the shared viewport slot as its last child |
| `List` | The `ul` list row (`data-slot="navigation-menu-list"`) wrapping the items |
| `Item` | The `li` item (`data-slot="navigation-menu-item"`) wrapping a trigger and its content anchor |
| `Trigger` | The trigger button carrying `data-value`, `aria-expanded`, `data-state`, and the chevron icon; its click announces `{ id, open }` on the document-level activation event |
| `Content` | The panel for a `value`: portals into the shared viewport slot and exits under `data-state="closed"` through `animationend` (or the 250ms budget) |
| `Link` | The leaf `a` link carrying `data-active="true"` for the accent styles |
| `Viewport` | The shared slot (`data-slot="navigation-menu-viewport"`) whose `data-state` tracks the store; every `Content` portals into it |
| `Indicator` | The moving underline that measures the active trigger against the bar and translates under it |

Every part spreads `class` and native attributes onto its element; parts own structure, styling stays in the wrapper.

### Options

| Option | Type | Default |
|---|---|---|
| `value` | `() => string` | internal signal |
| `onValueChange` | `(value: string) => void` | `-` |
| `viewport` | `boolean` | `true` |

## Key Concepts

### One Store, Announced Clicks

The trigger does not write the store: a trigger carrying `value` announces the requested state on the `hella:navigation-menu-activate` document event, and every mounted root mirrors the announcement into its own store. Opening one panel closes the others (one open at a time), and a second click on the open trigger closes the bar. The announcement stream is also what the indicator follows, so parts keep coordinating even when they render in different scopes.

### Content Renders Into the Shared Viewport

Every `Content` portals into the first `[data-slot="navigation-menu-viewport"]` in the document, the slot the root appends as its last child. The panel's enter and exit ride the viewport's `data-state`, so swapping panels animates the outgoing content before the viewport releases it. A `viewport` prop on `Content` names another portal target; with `viewport: false` on the factory, the root renders no slot and a manual `Viewport` (with an `id`) receives the panels.

### Exits Run Through a Grace Budget

Closing never unmounts immediately: the panel stays mounted under `data-state="closed"` until its `animationend` (or the 250ms fallback budget) removes it, and `onExited` fires as it leaves. Reopening mid-exit cancels the budget and keeps the panel mounted.

### Overrides for Manual Composition

`Trigger` takes `active` and `onActivate` to compose against external state; `Content` mirrors with `active`; `Viewport` and `Indicator` take `active`, and the `Indicator` takes an `anchor` resolving the trigger to sit under. Without overrides, each part defaults from the factory's store.

## Important Considerations

### Call the Factory in Component Scope

`navigationMenu()` creates the state signals that must dispose with the component that owns it. `Root` drops its announcement listener and `Indicator` its announcement and resize wiring at unmount; a module-level factory call leaks them. Call the factory inside the component that renders the parts.

### Values Are Global Trigger Names

The indicator resolves the active trigger by querying `[data-value='<id>']` for the announced id, so trigger values act as page-global names. Two bars reusing the same values would both mirror each other's announcements and measure each other's triggers; keep trigger values unique per page.

### No Panels Open on the First Render

Content panels portal into the viewport slot the root appends, and a portal resolving during the initial mount walk would run before that slot attaches. The store always starts closed (`""`); open a panel through a trigger click (or the controller's `value` write) after mount.

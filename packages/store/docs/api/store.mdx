# store

Converts a plain object into a deeply reactive store where primitives become signals, nested objects recurse into stores, Array/Map/Set values become granular collection containers whose object elements convert to element stores, and functions are preserved.

## API

```typescript
import { store } from '@hellajs/store';

// All properties writable (default)
function store<T>(initial: T, options?: StoreOptions<T>): Store<T>

// All properties readonly
function store<T>(initial: T, options: { readonly: true }): Store<T, keyof T>

// Specific properties readonly
function store<T, R extends readonly (keyof T)[]>(
  initial: T,
  options: { readonly: R }
): Store<T, R[number]>

// Middleware transformations only
function store<T>(
  initial: T,
  options: { middleware: StoreMiddleware<T> }
): Store<T, never>

// Specific properties readonly + middleware
function store<T, R extends readonly (keyof T)[]>(
  initial: T,
  options: { readonly: R; middleware: StoreMiddleware<T> }
): Store<T, R[number]>

type Store<T, R extends PropertyKey = never> = {
  [K in keyof T]:
    T[K] extends (...args: unknown[]) => unknown ? T[K] :
    T[K] extends unknown[] ? K extends R ? () => T[K] : Signal<T[K]> :
    T[K] extends Record<string, unknown> ? (K extends R ? Store<T[K], keyof T[K]> : Store<T[K]>) :
    K extends R ? () => T[K] : Signal<T[K]>;
} & {
  snapshot: () => Snapshot<T>;
  update: (partial: PartialDeep<T> | ((draft: Snapshot<T>) => void)) => void;
  cleanup: () => void;
  subscribe: <K extends SettableKeyOf<T>>(key: K, callback: (next: T[K], prev: T[K]) => void) => () => void;
}

// Keys of T that become signal-backed (settable) store properties.
// Function-valued keys and plain-object keys (nested stores) are excluded.
type SettableKeyOf<T> = {
  [K in keyof T]: T[K] extends (...args: unknown[]) => unknown ? never
  : T[K] extends Record<string, unknown> ? never
  : K;
}[keyof T];

// Recursively unwraps composed store types so Snapshot matches the plain
// values $snapshot() actually returns

type Snapshot<T> = {
  [K in keyof T]:
    T[K] extends Store<infer U, PropertyKey> ? Snapshot<U> : T[K];
}

interface StoreOptions<T> {
  readonly?: boolean | readonly (keyof T)[];
  middleware?: StoreMiddleware<T>;
  equals?: StoreEquals<T>;
}

type StoreMiddleware<T> = {
  [K in keyof T]?: T[K] extends (...args: unknown[]) => unknown
  ? (value: T[K]) => T[K]
  : T[K] extends unknown[]
  ? (value: T[K]) => T[K]
  : T[K] extends Record<string, unknown>
  ? StoreMiddleware<T[K]>
  : (value: T[K]) => T[K];
};

type StoreEquals<T> = {
  [K in keyof T]?: T[K] extends (...args: unknown[]) => unknown ? never
    : T[K] extends unknown[] ? EqualsFor<T[K]>
    : T[K] extends Record<string, unknown> ? StoreEquals<T[K]>
    : EqualsFor<T[K]>;
};

type EqualsFor<V> = ((previous: V, next: V) => boolean) | "structural";
```

- `initial`: Plain object to transform. Functions stay as-is, primitives become signals, plain objects recurse into nested stores, Array/Map/Set values become granular collection containers (`SignalArray`/`SignalMap`/`SignalSet` from `@hellajs/core`) with object elements converted to element stores.
- `options.readonly`: `true` for all properties readonly, or an array of keys to lock. Propagates deep: `true` locks every plain-object level; a listed object key locks its entire subtree. Composed stores keep their own readonly config.
- `options.middleware`: Per-key transform functions applied on every set.
- **Returns**: A reactive store with `$snapshot`, `$update`, `$cleanup`, and `$subscribe` methods.

### `$snapshot`

A reactive snapshot of the entire store state as a plain JavaScript object. The snapshot function is reactive and will re-compute when any store property changes.

> ⚠️ **Performance**: snapshot accesses every signal in the store. When composed stores are nested, the dependency footprint covers the full composed tree; any leaf signal change triggers re-computation. Use individual property access for targeted reactivity in wide or deeply composed stores. Writes that compare equal under the [`equals` option](#write-equality) never trigger re-computation.

```typescript
import { store } from '@hellajs/store';

const appStore = store({ count: 0, user: { name: 'Alice' } });

const snapshot = appStore.$snapshot();
console.log(snapshot); // { count: 0, user: { name: 'Alice' } }
```

The snapshot is reactive across composed store boundaries. When one store is nested inside another, mutating a leaf signal in either store triggers re-computation of the outer snapshot, and composed leaves unwrap to their plain values:

```typescript
import { effect } from '@hellajs/core';
import { store } from '@hellajs/store';

const userStore = store({ name: 'Alice' });
const appStore = store({ user: userStore });

effect(() => {
  console.log(appStore.$snapshot()); // { user: { name: 'Alice' } }
});

userStore.name('Bob'); // triggers the effect; snapshot is reactive across composed stores
```

### `$update`

Partial deep updates to the store state. Accepts either a partial object or a function that receives the current state.

For single property updates, set the property directly. For multiple properties or nested merges, use `$update()`. The call returns the store itself, typed with any keys the partial added (see [Growing Stores](#growing-stores)).

```typescript
import { store } from '@hellajs/store';

const appStore = store({ count: 0, step: 1, user: { name: 'Alice' } });

appStore.count(5);

appStore.$update({
  step: 2,
  user: { name: 'Bob' },
});

console.log(appStore.count());       // 5
console.log(appStore.step());        // 2
console.log(appStore.user.name());   // Bob
```

> ⚠️ `$update()` writes signal-backed properties, materializes unknown keys, and throws on everything else; nothing is silently dropped:
> - **Unknown key**: `$update({ newProp: 1 })` materializes `newProp` (a signal for leaves, a nested store for plain objects) and returns the store typed with it; see [Growing Stores](#growing-stores). The throw survives only for externally-replaced properties (redefined or deleted from outside the store), which stay `[store] $update: unknown key "newProp"`.
> - **Function property**: `$update({ onSave: fn })` throws `[store] $update: "onSave" is a function property, not state` ("assign it directly" in the full message). Swap functions by assigning directly: `appStore.onSave = newHandler`. A function value on a NEW key throws too: `[store] $update: key "onSave" cannot hold a function`.
> - **Reserved key**: `$update({ $snapshot: 1 })` throws `[store] $update: reserved key "snapshot"`.
> - **Store key with a non-object value**: `$update({ user: 'x' })` where `user` is a nested store throws `[store] $update: store key "user" requires an object value`.
> - **Readonly key**: writing a readonly property throws `[store] readonly key "<key>"`; the same error its setter call throws. Adding a new key to a readonly store throws the same error and nothing materializes.
> - **Replaced signal**: `$update()` through a settable key whose property was externally replaced (e.g. `outer.inner.value = 42` on a composed store) throws `[store] $update: settable key "value" must hold a signal, received number`; the received kind reflects `typeof` the replaced value.
>
> The draft path applies the same rules at runtime; its mutator is typed against the current shape, so draft additions materialize untyped. `$update()` throws at the first offending key, in partial-key order; keys processed before it are already applied.

### Growing Stores

Unknown keys materialize on their first `$update()` write, and the call returns the same store typed with the added keys: leaves become signals, plain objects become nested stores, and reads, later updates, `$snapshot()`, and `subscribe` all type the added key immediately. Capture the return to see the widening; the original reference keeps its narrower type (the `Object.assign` seam) while its runtime behavior, `$snapshot()` included, sees the added key right away.

```typescript
import { store } from '@hellajs/store';

const appStore = store({ count: 0 });

const withTags = appStore.$update({ tags: ['a'] });
withTags.tags();          // ['a'], a Signal<string[]>
withTags.$snapshot();      // { count: 0, tags: ['a'] }

const withUser = withTags.$update({ user: { name: 'Bob' } });
withUser.user.name();     // 'Bob', a Store<{ name: string }>

// ❌ appStore.$update({ count: 'x' });      // type error: existing keys stay validated
// ❌ appStore.$update({ $snapshot: 1 });      // throws: [store] $update: reserved key "snapshot"
// ❌ appStore.$update({ onSave: () => {} }); // throws: [store] $update: key "onSave" cannot hold a function
```

When future keys are known at creation, declare them optional in the type parameter instead: the store grows on the same binding with no captured reference, and reads are optional-chained because the property is absent until the first write materializes it.

```typescript
import { store } from '@hellajs/store';

// Declare the future key optional; the first write materializes it
const appStore = store<{ count: number; tags?: string[] }>({ count: 0 });

appStore.$update({ tags: ['a'] });
appStore.tags?.(); // ['a'], typed string[] | undefined

// Before the first write the property is absent: optional chaining reads
// undefined, and a direct appStore.tags() call is a type error
const fresh = store<{ count: number; tags?: string[] }>({ count: 0 });
fresh.tags?.(); // undefined

// Declared keys type draft additions too, unlike undeclared draft adds
appStore.$update(draft => { draft.tags = ['b']; });
```

Declared-optional keys subscribe once materialized (`$subscribe` throws for keys that were never written, like any absent key), and declared `middleware` and `equals` entries apply to them: options are keyed by the declared shape, so the entry runs at materialization and on every later write.

> ⚠️ **Nested future keys must not be declared optional.** An optional plain-object member types as a leaf signal rather than a nested store: the only compiling call form (`appStore.user?.()`) throws at runtime once the key materializes, while the runtime-correct `appStore.user.name()` stays a type error. Declare placeholder values for nested shapes instead: `store({ user: { name: '' } })` types every level up front with no future-key ceremony. Keep the returned-reference pattern above for nested shapes discovered at runtime.

Keys absent from the creation declaration get no middleware or [write equality](/learn/concepts/store-control#write-equality): both are keyed by the declared shape, so declare a key in the initial object or type parameter when it needs either. [`persistStore`](/reference/store/persiststore) hydrates through `$update()`, so persisted keys beyond the initial shape materialize on hydration. Nested stores grow through their own widened references: `withUser.user.$update({ age: 1 })` types `age` on the nested store (the parent's type is not re-derived).

### `$cleanup`

Recursively invokes `$cleanup` on each nested store. Individual signals are not disposed; they remain functional after cleanup, and the store object stays intact. Effects that read individual signals continue to fire.

```typescript
import { store } from '@hellajs/store';

const appStore = store({ count: 0, user: { name: 'Alice' } });
appStore.$cleanup();

appStore.count(10);
console.log(appStore.count()); // 10
```

### `$subscribe`

Observes changes to a single signal-backed property. The callback receives `(next, prev)`; the initial subscribe does not fire it; only subsequent changes do. For collection keys the subscription is container-level: structural operations and whole-collection writes fire it with fresh plain containers, while element field writes never touch the container and never fire it. Returns an unsubscribe function.

```typescript
import { store } from '@hellajs/store';

const appStore = store({ count: 0 });

const unsub = appStore.$subscribe('count', (next, prev) => {
  console.log(prev, '→', next);
});

appStore.count(5); // Logs: 0 → 5
unsub();
appStore.count(6); // silent; unsubscribed
```

- `key`: Name of a settable (signal-backed) property. Nested-store keys, function properties, reserved keys, and keys that were never added throw.
- `callback`: Receives the next and previous values. Runs untracked; reading signals inside it never widens the subscription. Skipped when a write compares equal to the current value.
- **Returns**: An unsubscribe function; calling it more than once is safe.

Unlike an [`effect`](/reference/core/effect) reading [`$snapshot()`](#snapshot), `$subscribe` tracks one property only (no whole-store dependency) and hands you the previous value, which effects never see. Writes inside [`batch`](/reference/core/batch)`()` fire the callback once per subscribed key when the batch ends.

Subscriptions belong to the store that owns the key: a composed parent exposes only its own signal-backed keys, so `appStore.$subscribe('user', cb)` throws; subscribe on the nested store itself:

```typescript
import { store } from '@hellajs/store';

const userStore = store({ name: 'Alice' });
const appStore = store({ user: userStore });

userStore.$subscribe('name', (next) => console.log(next));
appStore.user.name('Bob'); // Logs: Bob; shared signals fire the subscription
```

## Basic Usage

```typescript
import { store } from '@hellajs/store';

const appStore = store({
  count: 0,
  user: { name: 'Alice' }
});

appStore.count(5);
appStore.user.name('Bob');

console.log(appStore.count());       // 5
console.log(appStore.user.name());   // Bob
```

## Key Concepts

### Deep Reactivity

All nested objects become stores, Array/Map/Set values become granular collection containers with element stores, and functions stay as-is, a fully reactive state tree. See [State](/learn/concepts/state) for the deep walk and effect examples, the [deep collection keys](/learn/concepts/state#deep-collection-keys) section for the granularity matrix, and [Store Control](/learn/concepts/store-control) for [middleware](/learn/concepts/store-control#middleware) and [readonly](/learn/concepts/store-control#readonly) configuration.

### Nested Stores

Existing stores compose as values: `store({ user: userStore })` nests the store with shared signal references, so writing through either reference updates the same signals. See [State](/learn/concepts/state) for what composed stores provide and [`$snapshot`](#snapshot) for reactive composed snapshots.

### Partial Updates

Pass a partial object to `$update()` for deep merging nested properties; unknown keys materialize and widen the returned store. See [State](/learn/concepts/state) for the pattern.

### Mutable Updates

Pass a function to `$update()` for ergonomic mutations on a mutable draft of the state. See [State](/learn/concepts/state) for array-operation examples.

### Write Equality

By default every write is reference-compared; the `equals` option replaces that per key with a comparator function or the `'structural'` content-equality preset, inherited by every write path (direct calls, `$update(partial)`, and the draft path). For collection keys the comparator applies per element: it receives two elements (two values for a Map), never two whole collections. See [write equality](/learn/concepts/store-control#write-equality) for the option shape, invalid-value errors, and the O(n) cost note.

### Function Preservation

Functions in the initial object are preserved as-is, not wrapped in signals, functional in snapshots. Snapshots preserve the **original** initial function references; a handler swapped in later (`appStore.onSave = newHandler`) is not what `$snapshot()` returns. See [State](/learn/concepts/state) for `computed`-in-store examples.

### `PartialDeep<T>`

Recursive optional mapping used by [`$update()`](#update).

```typescript
type PartialDeep<T> = {
  [K in keyof T]?: T[K] extends (...args: unknown[]) => unknown
  ? T[K]
  : T[K] extends unknown[]
  ? T[K]
  : T[K] extends Record<string, unknown>
  ? PartialDeep<T[K]>
  : T[K];
};
```

- **`T`**: The object type to make partially optional.

> ⚠️ `PartialDeep` preserves arrays and functions without recursing into them. A partial update to `{ items: [...] }` writes the whole array through the container's reconcile: object elements at existing positions patch in place, equal positions write nothing, and length differences restructure.

### `ReadonlyKeys<T, O>`

Extracts the readonly property key set from a `StoreOptions` value. Useful for deriving the readonly keys of a store at the type level. See [readonly](/learn/concepts/store-control#readonly) for usage.

```typescript
type ReadonlyKeys<T, O extends StoreOptions<T> | undefined> =
  O extends { readonly: true }
  ? keyof T
  : O extends { readonly: readonly (keyof T)[] }
  ? O["readonly"][number]
  : never;
```

- **`T`**: The store's value type.
- **`O`**: The `StoreOptions<T>` or `undefined`.

Applied: `{ readonly: ['apiUrl'] }` resolves to `'apiUrl'`, `{ readonly: true }` to `keyof T`, and `undefined` to `never`.

## Important Considerations

### Draft Updates Compare Structurally

The `$update(fn)` draft path diffs by content, not reference. Untouched `Date`, `Map`, `Set`, `RegExp`, and array values are not rewritten; their signals keep the same value and subscribers do not fire. Mutated class instances keep their prototype:

```typescript
import { store } from '@hellajs/store';

class Point {
  x: number;
  constructor(x: number) { this.x = x; }
}

const data = store({ point: new Point(1), count: 0 });

data.$update(draft => {
  draft.count = 1; // point is untouched; no write, no subscriber wakeups
});

data.$update(draft => {
  draft.point.x = 5; // written back as a Point, not a plain object
});
```

### Reserved Keys

The keys `$snapshot`, `$update`, `$cleanup`, and `$subscribe` are reserved by the store implementation. Passing them as properties in the initial object throws an error.

```typescript
import { store } from '@hellajs/store';

store({ $snapshot: 1 }); // Throws: Error '[store] store: reserved key collision, received "$snapshot"'
```

### Memory Management

`$cleanup()` propagates teardown through the store tree, invoking each nested store's `cleanup`. Assign a custom `cleanup` method to release external resources (timers, listeners, subscriptions); the call recurses through the whole tree.

```typescript
import { store } from '@hellajs/store';

const userStore = store({ name: 'John' });
userStore.$cleanup();
```

### Readonly Propagates Deep

`readonly: true` locks every plain-object level of the store tree, and a listed object key locks its entire subtree. Composed stores are the exception: adoption preserves their signals, so a composed store keeps its own readonly configuration regardless of the parent's. See [readonly](/learn/concepts/store-control#readonly) for the full explanation and examples.

### Signals Survive Cleanup

`$cleanup()` recursively invokes `cleanup` on nested stores but does not dispose individual signals or null the store object. This is intentional: signals owned by other contexts (composed stores, external effects) keep working.

### Store Properties Are Non-Writable

Signal-backed properties, nested stores, and the built-in methods are defined non-writable; external reassignment (`appStore.count = 5`) throws a `TypeError` in strict-mode ESM instead of silently dropping reactivity. Write through the signal (`appStore.count(5)`), or `$update()`. Function-valued properties are the exemption: they stay writable so handlers can be swapped (`appStore.onSave = newHandler`), including the adopted signal functions of composed-store leaves.

### Effects vs Middleware

- **Effects** run after changes: use for logging, persistence, derived state.
- **Middleware** runs before changes: use for validation, transformation.

```typescript
import { effect } from '@hellajs/core';
import { store } from '@hellajs/store';

const data = store({ count: 0 }, {
  middleware: { count: (v) => Math.max(0, v) }
});

effect(() => {
  console.log('Count changed:', data.count());
});
```

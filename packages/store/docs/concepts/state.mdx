# State

Signals are the foundation for all reactive state in HellaJS. Use them directly for local component state or module-level shared state — and when state grows into a nested object shared across components, reach for a [`store`](/reference/store/store). See [Reactivity](/learn/concepts/reactivity) for the signal model itself.

## Creating Stores

A [`store`](/reference/store/store) converts a plain object into deeply reactive state where each property is an independently reactive signal. Only the specific properties that change trigger re-computation.

```typescript
import { store } from '@hellajs/store';

const counter = store({
  count: 0,
  step: 1,
  guards: {
    min: 0,
    max: 10
  }
});

// Each property is individually reactive
counter.count();        // 0
counter.step();         // 1
counter.guards.max();   // 10

// Set individual properties directly
counter.count(5);
counter.step(2);
```

## What Stores Provide

Beyond basic get/set, stores offer several capabilities, each documented in detail in the [`store`](/reference/store/store) reference.

- **Readonly**: Restrict specific properties or the entire store to read-only access, enforced at the type level.
- **Snapshots**: Get a plain object representation of the entire store state. Reactive: recomputes when any property changes.
- **Updates**: Apply partial deep merges or mutate a draft directly for ergonomic multi-property and array changes.
- **Middleware**: Validate and transform values before they're stored. Runs synchronously on every set operation.
- **Nested stores**: Compose stores hierarchically. Nested stores share signal references bidirectionally.
- **Batching**: Wrap multiple store updates in [`batch`](/reference/core/batch) to defer computation until all changes are applied.
- **Cleanup**: Recursively propagate teardown to nested stores when the store is no longer needed.

## Deep Reactivity

All nested objects are automatically converted to reactive stores, arrays become signals, and functions remain unchanged, creating a fully reactive state tree.

```typescript
import { effect } from '@hellajs/core';
import { store } from '@hellajs/store';

const userStore = store({
  profile: { name: 'John', age: 30 },
  settings: { theme: 'dark' }
});

effect(() => {
  console.log(userStore.profile.name());
  console.log(userStore.settings.theme());
});
```

## Updating Stores

### Partial Updates

Pass a partial object to `update` for deep merging nested properties.

```typescript
import { store } from '@hellajs/store';

const user = store({
  profile: { name: 'John', email: 'john@example.com' },
  settings: { theme: 'light', notifications: true }
});

user.update({
  profile: { name: 'Jane', email: 'jane@example.com' }
});

console.log(user.profile.name()); // Jane
console.log(user.settings.theme()); // light (unchanged)
```

### Mutable Updates

Pass a function to `update` for ergonomic mutations on arrays and complex nested transforms. The function receives a mutable draft.

```typescript
import { store } from '@hellajs/store';

const todos = store({
  items: [
    { id: 1, text: 'Learn HellaJS', done: false },
    { id: 2, text: 'Build app', done: false }
  ],
  count: 2
});

todos.update(draft => {
  draft.items.push({ id: 3, text: 'Ship it', done: false });
  const first = draft.items[0];
  if (first) first.done = true;
  draft.count = draft.items.length;
});

console.log(todos.items().length); // 3
console.log(todos.items()[0]?.done); // true
```

## Middleware

Transform or validate values before they are stored. Middleware runs synchronously on every set operation for the configured properties.

```typescript
import { store } from '@hellajs/store';

const user = store({
  name: '',
  email: '',
  age: 0
}, {
  middleware: {
    name: (v) => v.trim(),
    email: (v) => v.toLowerCase(),
    age: (v) => {
      if (v < 0) throw new Error('Age cannot be negative');
      return v;
    }
  }
});

user.name('John');              // stored as 'John'
user.email('john@example.com'); // stored as 'john@example.com'
user.age(-5);                   // throws Error
```

Middleware also applies through `update()`:

```typescript
user.update({ name: 'Jane', age: 30 });
user.update(draft => { draft.email = 'jane@example.com'; });
```

Middleware works with nested stores too. Middleware for nested objects must be a nested object mapping individual property keys to their middleware functions:

```typescript
const app = store({
  user: { name: '', email: '' },
  settings: { theme: 'light' }
}, {
  middleware: {
    user: {
      name: (v) => v.trim(),
      email: (v) => v.toLowerCase()
    },
    settings: {
      theme: (v) => {
        if (!['light', 'dark'].includes(v)) throw new Error('Invalid theme');
        return v;
      }
    }
  }
});
```

Middleware runs *before* changes are stored — use it for validation, transformation, or normalization. Effects run *after* — see [reactivity](/learn/concepts/reactivity) for logging, persistence, and derived-state patterns.

## Readonly

Granular control over which properties can be modified, enforced at the type level.

```typescript
import { store } from '@hellajs/store';

const configStore = store(
  { apiUrl: 'https://api.com', theme: 'light', debug: false },
  { readonly: ['apiUrl'] as const }
);

configStore.theme('dark');           // Updates normally
// ❌ configStore.apiUrl('new-url'); — throws: readonly key
```

Readonly keys do not propagate to nested stores. Each nested store requires its own readonly configuration. Pre-configured readonly stores retain their readonly state when composed:

```typescript
import { store } from '@hellajs/store';

const user = store({ name: 'Alice' }, { readonly: true });
const app = store({ user });

// ❌ app.user.name('Bob'); — throws: user retains its readonly state
app.user.name();      // 'Alice'
```

## Important Store Behaviors

### Update Errors

The `update()` method only applies changes for properties that exist in the initial object and are backed by signals. Writes outside that contract throw an `Error` naming the offending key — nothing is silently dropped:

```typescript
import { store } from '@hellajs/store';

const app = store({
  count: 0,
  user: { name: 'Alice' },
  onSave: () => {}
});

app.update({ count: 5 });              // ✅ works — count is in the initial object
app.update({ user: { name: 'Bob' } }); // ✅ works — nested stores accept object partials

// ❌ app.update({ newProp: 'value' }); // throws: [store] update: unknown key "newProp"
// ❌ app.update({ onSave: () => {} }); // throws: [store] update: "onSave" is a function property, not state — assign it directly
// ❌ app.update({ snapshot: 1 });      // throws: [store] update: reserved key "snapshot"
// ❌ app.update({ user: 'x' });        // throws: [store] update: store key "user" requires an object value
```

Readonly keys throw on every write path — `update()`, the direct setter call, and the draft path:

```typescript
import { store } from '@hellajs/store';

const locked = store({ apiKey: 'a', count: 0 }, { readonly: ['apiKey'] as const });

// ❌ locked.update({ apiKey: 'b' }); // throws: [store] readonly key "apiKey"
// ❌ locked.apiKey('b');             // throws: [store] readonly key "apiKey"
```

The draft path applies the same rules: assigning a function property or an unknown key inside `update(draft => ...)` throws when the changes are extracted and applied.

`update()` throws at the first offending key, in partial-key order — keys processed before the offending one are already applied. Validate input before calling `update()` if you need all-or-nothing semantics.

### Non-Writable Properties

Signal-backed properties, nested stores, and the built-in methods (`snapshot`, `update`, `cleanup`) are defined non-writable. External reassignment would replace the signal with a plain value and silently drop reactivity, so in strict-mode ESM it throws instead:

```typescript
import { store } from '@hellajs/store';

const app = store({ count: 0 });

// ❌ app.count = 5; — TypeError: signal-backed properties are non-writable
app.count(5); // ✅ write through the signal
```

Function-valued properties are the exemption — they stay writable so handlers can be swapped (`app.onSave = newHandler`). This includes the adopted signal functions of a composed store's leaves, whose replacement remains possible for the same reason.

### Function Preservation

Functions in the initial object are preserved as-is. They are not wrapped in signals and remain unchanged in the store and snapshot.

```typescript
import { computed } from '@hellajs/core';
import { store, type Store } from '@hellajs/store';

type DataStore = Store<{
  count: number;
  double: () => number;
  logCount: () => void;
}>;

const data: DataStore = store({
  count: 0,
  double: computed(() => data.count() * 2),
  logCount: () => console.log('Count is', data.count()),
});

data.count(1);
data.logCount(); // Count is 1
data.double();   // 2

// Functions remain functional in snapshots
const snap = data.snapshot();
snap.logCount(); // Count is 1
```

### Reserved Keys

The property names `snapshot`, `update`, and `cleanup` are reserved by the store implementation. Using them as property names in the initial object will throw an error.

```typescript
// Throws: Error '[store] store: reserved key collision, received "snapshot"'
store({ snapshot: 1, name: 'test' });

// Throws: Error '[store] store: reserved key collision, received "update"'
store({ update: () => {}, value: 42 });

// Valid property names
store({ data: 123, info: 'hello' }); // works fine
```

<summary>Internal Mechanics</summary>

A regular object becomes a reactive store by wrapping its primitive properties in signals.

### Store Architecture

Each store is a **reactive object** that converts object properties into reactive primitives.

```
Store Object
├── Property A → Signal<T>
├── Property B → Signal<T>
├── Readonly Property → Computed<T> (wraps Signal<T>)
└── Nested Store
    ├── Property C → Signal<T>
    └── Property D → Signal<T>
```

### Property Transformation

When a store is created, the system transforms each property based on its type and characteristics.

- **Primitive values** (strings, numbers, booleans) become individual signals
- **Objects** become nested stores with recursive property transformation
- **Arrays** become signals containing the array value
- **Functions** remain unchanged, preserving their original behavior

Signal-backed properties, nested stores, and the built-in methods are defined with `writable: false` — external reassignment throws a `TypeError` instead of silently dropping reactivity. Function-valued properties keep `writable: true` so handlers stay swappable.

### Update Propagation

Store updates follow the same efficient propagation mechanism as the core reactive system.

1. **Property Change** - A store property is updated via signal function call
2. **Dependency Marking** - Only computations dependent on that specific property are marked dirty
3. **Selective Propagation** - Changes propagate only through affected dependency chains
4. **Lazy Evaluation** - Computed values recalculate only when accessed AND dependencies changed
5. **Effect Execution** - Effects are queued and flushed in dependency order after the current write completes (glitch-free)

### Memory Efficiency

The store system includes several memory optimization strategies.

- **Automatic Cleanup** - `cleanup()` recursively invokes teardown on nested stores; individual signals are not disposed
- **No Cycle Detection** - Self-referential initial objects will recurse until the stack overflows; store initial state must be a tree
- **Efficient Updates** - The `update()` function variant compares the draft to the current state structurally: Dates, Maps, Sets, RegExps, class instances, and arrays compare by content, so untouched values are never rewritten and effects subscribed only to untouched properties do not fire

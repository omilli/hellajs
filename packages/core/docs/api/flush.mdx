# flush

Drains the scheduled-effect queue, running every queued [`effect`](/reference/core/effect) synchronously.

## API

```typescript
function flush(): void
```
- **Returns**: Nothing. Every queued effect runs before the call returns.

## Basic Usage

An error thrown inside an effect aborts the drain and leaves the remaining queued effects waiting. Call `flush()` to run them at a known point:

```typescript
import { signal, effect, flush } from '@hellajs/core';

const count = signal(0);
const events: string[] = [];

effect(() => events.push(`first: ${count()}`));

let runs = 0;
effect(() => {
  count();
  if (++runs > 1) throw new Error('boom'); // Throws on re-run only
});

effect(() => {
  count();
  events.push('third effect ran');
});

try {
  count(1); // First effect runs, the second throws: the drain aborts
} catch {
  // The error surfaces at the write that triggered it
}

flush(); // Runs the third effect left queued by the aborted drain
console.log(events); // Logs: ["first: 0", "third effect ran", "first: 1", "third effect ran"]
```

## Key Concepts

### Automatic Draining

The queue drains without an explicit call: a [`signal`](/reference/core/signal) write outside [`batch`](/reference/core/batch) flushes before the setter returns, and the outermost `batch` flushes on exit. At rest the queue is empty, so an explicit `flush()` is a no-op — it earns its keep in tests and integration code that catch effect errors and need the leftover queue drained deterministically.

### Same-Pass Scheduling

Effects scheduled while a drain is running are appended to the queue and run in the same pass — no second flush needed.

```typescript
import { signal, effect } from '@hellajs/core';

const src = signal(0);
const trigger = signal(0);
const events: string[] = [];

effect(() => trigger(src()));
effect(() => events.push(`trigger is ${trigger()}`));

src(1); // First effect writes trigger mid-drain; the second is appended and runs in the same pass
console.log(events); // Logs: ["trigger is 0", "trigger is 1"]
```

### Error Recovery

A throw inside an effect unwinds out of the write or `flush()` call that triggered it, keeping the remaining queue entries intact. The next flush — an explicit `flush()` or the next un-batched write — picks up where the drain stopped; reactive state is never corrupted. See [error propagation](/reference/core/effect#error-propagation) for the full effect error rules.

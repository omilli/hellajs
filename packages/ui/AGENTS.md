<ui-package-instructions>
  Copy/paste component registry and its CLI: `bunx @hellajs/ui add <component>` copies owned, editable source into the user's project; there is no importable component surface. The npm artifact IS the CLI (`bin/hellajs-ui.js` runs `main` from `dist/index.js`). `lib/` imports only `node:` builtins plus its single runtime dependency, `esbuild` (`stripTypes`; the bundle externals rule keeps the JS API external in `dist`), so the package still bundles standalone; the `@hellajs/*` peers are convention-declared, never imported here.

  ## Registry

  Copy/paste source owned by this package; there is no importable component surface. ONE canonical component file per component — `registry/<name>/<name>.tsx` (jsx) — carrying only markup, props, marker regions, and the types import: exactly one `// @hella:styles` (carrying ambient `declare const` placeholders for the splice-injected style names so the canonical standalone-typechecks; the region body is discarded when the style module's body splices here) and one `// @hella:compose` per styled part (the live css class array), each closed by `// @hella:end`. Shared types live ONCE in the conventional `<name>-types.ts` module the canonical imports (`import type { … } from "./<name>-types.js";` after the last import) — never copied as a file; `inlineTypes` splices the module body at that import site in BOTH `addComponent` and the compile step, so the copied and compiled output stay one standalone file (previously-exported canonical types re-export through `export type { X };`). The style declarations live ONCE per style in real TS modules named by convention `<name>-<style>.ts` (`button-css.ts`: unlayered `style()` maps; `button-tailwind.ts`: plain string maps) — exported bindings, one string map or class per styled part that carries classes (lowerCamel part names: `header`, `title`, …; `variants`/`sizes` optional; an empty-string binding exists only as a css/tailwind style bridge, never for an unstyled part), never copied as files. Shared entries live in `registry/theme/` (`tokens.ts` css, `tokens.dark.ts` dark-default css, `theme.css` tailwind) and `registry/cn/` (`cn.ts`, tailwind only). The css sheets export `tokens = vars({ camelCase keys })`; each key resolves to its `var(--kebab)` reference. `add` splices the chosen style module into the canonical through `applyStyleVariant`: package imports ride along verbatim, the theme import `../theme/tokens.js` is the sole relative allowance and rewrites to `./tokens.js` (the copied sheet sits beside the components), `export ` prefixes strip, the tailwind style inlines every string declaration at its use site (compose members, static class attributes, outside references, and canonical runtime constants; keyed maps stay in the styles region, and a same-named local binding keeps the declaration as a conservative fallback), wraps every compose array in `cn(…)` and injects `import { cn } from "./cn.js";` after the last import. Markers never ship; the CLI owns all marker processing — babel and the user's build never see one.

  Registry data schema: shared `files`/`deps` at entry level; per-style slots carry only the slot's delta (extra deps, registryDependencies, and a `darkFiles` target→source map whose sources copy in place of the mapped target files when the resolved `themeMode` is `dark`). Style modules and types modules are NOT manifest data — an entry with shared files owns `<name>-<style>.ts` and `<name>-types.ts` by convention (`resolveEntry` derives both; the registry integrity test enforces both). Style-scoped shared entries (theme, cn) keep everything in their slots — `resolveEntry` unions shared fields with the slot's.

  Gotchas — non-obvious, load-bearing:

  - **Class-array members are static values.** Public parts carry the rest-attrs contract: the props interface extends `HTMLAttributes<"root">` with a narrowed `class?: string` re-declaration (HTMLAttributes types `class` as the `HellaPrimitive | (string | null | undefined | boolean)[]` union — without the narrowing the compose attribute fails TS2322), the signature destructures `{ class: cls, ...attrs }` so `cls` is the compose array's FINAL member and `{...attrs}` / `...${attrs}` spreads LAST onto the root (user attributes win), and a part that owns a handler chains the user's prefixed key: destructure `"on:click": userClick` and emit a merged handler calling `userClick?.call(this, e)` before the internal toggle (checkbox.tsx/switch.tsx shape). Internal builders needing a class hook on a native node name it non-natively (`dayClass`, calendar's DayCellProps) — a native attribute is never an explicit prop. The css flavor composes each part's class as a plain array (the `@hella:compose` region body; Button keeps `variants[…]`/`sizes[…]` lookups), joined by dom's `renderProp` (`filter(Boolean).join(" ")`). A reactive member string would stringify as source, not resolve — class composition is static by design; precedence between registry CSS and user CSS follows cascade order (registry declarations register unlayered, so author stylesheets loaded after the registry theme win equal-specificity ties), not a class-name compositor's. The compose body must BE a plain array — the tailwind wrap (`[`` → `cn(`) throws without it. The tailwind flavor inlines every string constant at its use site (`cn("inline-flex …", variants[…])`): `classifyDecls` splits module and canonical blocks, `codeMask`/`matchKind` classify each name occurrence (comments, imports, string content, property signatures, JSX tags, and attribute names never count as references; a same-named local binding keeps the const as a conservative fallback), `inlineStringDecls` gates and `substituteLiterals`/`inlineComposeMembers` apply — literals land at compose members, static `class={name}`/`class="${name}"` attributes, bare outside references, and canonical runtime constants (which drop with their comments). Canonical same-named locals are renamed so the fallback never fires (field's separator rule and command's icon span inline at their unmarked sites too); extending compose markers there would change `cn()` conflict semantics.
  - **Dark mode is the `.dark` ancestor class, and ancestor-conditioned styling cannot use non-`&`-first selectors.** The css package's `style()` nesting replaces `&` only in `&`-FIRST keys, so `.dark &`-style ancestor selectors would emit a literal `&` (broken CSS). `.dark` conditions translate to `&:is(.dark *)` (shadcn v4's own variant definition); ancestor-attribute conditions (Tabs' trigger-under-`[data-variant=line]`-list, Card's `[.border-b]` sibling) register as raw attribute selectors under a plain `css({ … })` call in the same style module, placed AFTER the `style()` calls (equal-specificity cascade resolves by registration order within the sheet). Keyframes for css-flavor animations come from `keyframes()` (hashed names referenced in `animation` values), never hand-named `@keyframes`.
  - **JSX canonical components are typed `: JSX.Element`** (dom's global `JSX.Element = HellaNode & RenderFn`), not `: HellaNode` — the `.d.ts` emission and user-side JSX usage reject a bare-`HellaNode` return with TS2786. Multi-part canonicals also pass arrays through explicit `children={[...]}` props, NOT JSX child slots: a `HellaChildren`-typed value through a child slot double-wraps and fails the `HellaChild` element check.
  - **Compound children evaluate once — arrow-wrap them.** The transform concat-splices a bare `props.children` member reactively, but a COMPOUND child expression (`{props.children ?? fallback}`) is not that bare member, so it evaluates once as a static value — correct only while the value never changes. Arrow-wrap every conditional/compound child (`{() => props.children ?? fallback}`). Pass-through parts (`TabsList`, `DialogHeader`, …) keep fixed innards (the DialogClose X + `sr-only` span) inlined in the part's own markup rather than passed as children (per-call node identity; static-subtree sharing moves nodes between clones).
  - **Items props render through `ForEach`, never `.map()`.** An items prop accepts `Entry[] | (() => Entry[])`: a plain array is a mount-time snapshot (mapping a static array reads no signal, so the list effect runs once with zero dependencies and a dynamic list silently never updates), while a getter resolves inside ForEach's own effect. Keying defaults to index (reference-compare rebuild keeps swapped static content fresh; reorders/prepends rebuild and lose transient state); `keyBy?: "value"` opts into value-identity reuse — pass the value as `key` on the rendered root: `renderProp`/`serializeProp` skip `key`, so it reaches ForEach's `resolveItemKey` as reconciliation metadata and never renders. Tabs' `TabsItem.id` auto-keys through `resolveItemKey`'s chain (explicit `key` → `item.id` → index) — no `keyBy` prop there. Keys never affect order: DOM order always equals the `each` array order (LIS only minimizes moves). Key-reused nodes don't re-render static children — a same-key label/trigger swap needs getter-wrapped content. Never destructure-and-drop a `key` the root must forward: `resolveItemKey` reads the rendered root's `props.key` — the same channel the attrs spread feeds — so dropping it severs reuse and silently falls back to index keys.
  - **Function-valued attribute expressions and nested function children stringify.** babel's `maybeReactive` wraps compound attribute expressions in an outer arrow; when the expression's VALUE is itself a function (a ternary yielding an accessor), the runtime receives arrow-in-arrow and `renderProp` stringifies the inner one into the attribute — observed as `style="() => props.hidden() ? …"` in compiled output. Precompute the accessor as a bare const binding (`const hiddenStyle = props.hidden ? () => … : undefined` then `style={hiddenStyle}`) in both flavors, and give a part that must render reactive children through a passthrough slot a purpose-built thunk prop instead (`portal?: () => HellaChildren`, ComboboxChips' `chips`) — `{() => props.children}` with function-valued children stringifies the same way (`resolveValue` unwraps exactly one level).
  - **A reactive structural branch must resolve to a vnode in one unwrap.** `appendToParent` → `resolveValue` unwraps a branch thunk once; an arm returning a render-fn, or an array with fn members, stringifies as `[object Object]` text because `resolveNode` treats the leftover fn as reactive TEXT. Compose the fork so each arm yields a vnode: internal gate builders return the gate thunk and the branch arm CALLS it (`mobileTree()`, sidebar's `SidebarMobileSheet`).
  - **The Dialog export gates its render on an internal `visible` signal, not `open()` directly.** Reading `open()` in the render template unmounts the subtree one evaluation before the open-watcher effect starts the exit (signal write vs template effect ordering); `visible` is written only by the watcher, so the exit holds the panel mounted until its `animationend` (or the 250ms fallback). The exit runs unwired: DialogContent's state effect disposes the trap/escape/outside wirings the moment `state` flips `"closed"` and re-arms them on reopen without a remount.
  - **Marker lines must stay standalone** — `// @hella:…` occupies its own line (leading whitespace fine, e.g. the compose region inside JSX attribute braces); trailing code on a marker line breaks the section parser, and any UNKNOWN `@hella:` marker throws (a stale three-region canonical fails loudly instead of shipping inert comments). The registry integrity test enforces exactly one `@hella:styles` plus at least one `@hella:compose` per canonical, with a matching `@hella:end` for each.
  - **Style modules are package-import-only.** `parseStyleModule` rejects relative/absolute specifiers — spliced output lands in a foreign flat directory, so a relative path from `registry/<name>/` would dangle. The only cross-file import a spliced file carries is the engine-injected `import { cn } from "./cn.js";` (the `.js` suffix is load-bearing: the per-module build's specifier fixup appends `.js` to extensionless relative imports — string literals included — so the constant must already hold the final form to stay identical across dist shapes; and `./cn.js` is the TS convention resolving to the copied `cn.ts` in the user's project). `export default` / `export {…}` in a style module throws; bare `export const` prefixes are stripped on splice.
  - **Types modules follow the style-module import rule.** `resolveEntry` derives `<name>-types.ts` beside the canonicals; both `addComponent` and the compile step read it strictly (a component entry whose module is missing fails loud — ENOENT at add, the named `[bundle]` throw at build) and inline it at the canonical's `import … from "./<name>-types.js";` site through `inlineTypes` (package imports ride along, `export ` prefixes strip, relative/absolute specifiers and `export default`/`export {…}` throw) — the copied output inlines the shared types at the import site and stays one standalone file per format. Types previously exported from a canonical re-export through `export type { X };` after the import block (accordion `AccordionEntry`, command `CommandItemData`, sonner `ToastApi`, tabs `TabsItem`), so the copied file's public type surface is unchanged.
  - **Delegated `on:` handlers must extract event data from `e.target`, never `e.currentTarget`.** dom's delegation runs one capture listener per event type on `document.body` and invokes `handler.call(element, event)` — `this` is the element but `currentTarget` stays the body, so `e.currentTarget.value` is `undefined` (the optional chain then silently passes it on). `currentTarget` is the element only under the direct `e:` prefix; `e.target` is correct everywhere (`input.tsx` shape: `(e.target as HTMLInputElement).value`).
  - **Css style modules import the theme sheet; every other registry file stays standalone.** `*-css.ts` modules open with `import { tokens } from "../theme/tokens.js";` and read palette values as `tokens.x` / `sidebarTokens.x` member references (sidebar's own `vars({ sidebarForeground, … })` block binds locally as `sidebarTokens`, never exported — style-module exports strip on splice). The transform rewrites that one exact specifier to `./tokens.js` on splice; every other relative/absolute specifier still throws the package-specifiers error. Tailwind style modules, canonicals, and `cn.ts` keep only `@hellajs/*` peer imports (plus `clsx`/`tailwind-merge`); the theme is added ONCE per app (user entry) — this is why `init` adds `theme` separately. Custom-property names stay kebab everywhere (`tokens.primaryForeground` evaluates to `var(--primary-foreground)`); without the theme anywhere the properties resolve to nothing.
  - **Tailwind flavor is theme.css-only** — zero `@hellajs/css` references anywhere in the tailwind style module or its copy output; the palette is plain CSS wrapped in a whole-file cascade layer, read through v4 arbitrary-value shorthands (`bg-(--primary)`). Opacity modifiers on var shorthands are verified (`bg-(--primary)/90` → `color-mix(in oklab, …)` chain, probed against tailwindcss 4.1.18). Bounded open: tailwind-merge v4-syntax support for `bg-(--primary)` arbitrary-value conflict resolution is deferred (tailwind-merge ^3 in devDependencies for style-module typechecking).
  - **`clsx`/`tailwind-merge` are devDependencies, not peers.** `cn.ts` is user-owned template code importing the user's deps (`checkPeers` demands them at add time); the devDeps exist only so the lint program typechecks `cn.ts` and the style modules with real types. Never promote them to `peerDependencies` (memory 023: all-peer convention for `@hellajs/*`).
  - **`sonner` is the registry's first non-component export**: the canonical carries a module-level singleton (`toasts` signal + timer/instance state) beside the `Toaster` component, so one copied file owns one queue per app and `add` needs no engine change. Two consequences are load-bearing: per-toast live-element wiring (timers, hover pause, swipe) rides a module-level `$ref` registered once at enqueue time in `wireToast` — NOT `hook:afterMount` in the li, because lis slot into the portaled ol after its one-and-only mount walk and only mount/hydrate roots and Portal insertions deliver hooks — and the `$ref` selectors carry an `INSTANCE` nonce because ForEach's effect re-invokes `use` on every queue write (body-side registration would duplicate selectors) while both compiled styles of the same source coexist in tests.
  - **Lint wiring for registry files**: `tsconfig.lint.json` carries `"jsx": "preserve"` (global JSX namespace, examples convention) and includes `registry/**/*.ts` + `**/*.tsx` + `**/*.js` — covering style modules, `cn.ts`, `tokens.ts`, AND the canonicals: each canonical's `// @hella:styles` region carries ambient `declare const` placeholders for the splice-injected names (`base`, `variants`, `sizes`, …), so canonicals standalone-typecheck. eslint ignores no registry glob (its only ui-specific ignore is `packages/ui/tests/.tmp/**`, e2e scratch). The compile step's `.d.ts` emission over the spliced variants still runs (§Compile step), but the standalone gate is `bun coverage ui` (repo-wide tsc + scoped eslint).

  ## Compile step (`dist/registry`)

  `bun bundle ui` compiles the registry to `dist/registry/**` via `scripts/bundle/registry.ts` — build/verification output only, never shipped (`files` carries explicit top-level `dist/*` globs + `dist/internal`, so `dist/registry` stays out of the tarball). **Never edit `dist/registry` by hand** — `registry/` is the only truth; a registry or style-module edit invalidates the build cache (`isCacheValid` hashes the package dir) and recompiles on the next bundle.

  - **Layout**: entry-level (shared) files → `dist/registry/<name>/<style>/<file>.js`; style-scoped entries flat → `dist/registry/theme/{tokens.js,tokens.dark.js,tokens.d.ts,tokens.dark.d.ts,theme.css}` (sheets compiled from the staged `tokens.ts` sources; `theme.css` verbatim), `dist/registry/cn/cn.js` (compiled). Tailwind variant dirs additionally carry the compiled shared dep modules (`cn.js`) so the injected `./cn.js` import resolves in dist; css variant dirs additionally carry the compiled `tokens.js` + `tokens.d.ts` the dependency pass stages beside each canonical so the spliced `./tokens.js` import resolves for declaration emit — compiled entries themselves import `../../theme/tokens.js` (the `compileFile` specifier rewrite), so the per-dir copies stay unreferenced by code.
  - **Docs site, no dist consumer**: the site no longer imports `dist/registry` — the root `bun docs-ui` script consumes the public API (`addComponent`/`loadRegistry` from `dist/index.js`) to generate the committed site set: the live css-jsx set + tokens sheet under `docs/src/components/ui/` and the two `add`-output variant dirs under `docs/src/ui-install/{css-jsx,tailwind-jsx}/`. `docs/src/demos/<name>-demo.tsx` (named export blocks only) import the generated set via `@components/ui/<name>.js`, and `docs/src/components/Component.astro` mounts them (interactive demos via `client:load` on the element the page passes) through the `astro-plugin-hellajs` renderer, owning the single generated-theme-sheet import (`../components/ui/tokens.js`, the light sheet — the site is dark-only); `CodeExample` + `docs/src/utils/example-code.ts` slice each named export's raw source for View Code; site code imports no ui internals; `dist/internal` is not a supported surface — there are no package-side demos. A registry edit that changes `add` output reaches the site after `bun bundle ui && bun docs-ui`.
  - **One transform, two callers**: the build compiles through the same babel options `plugins/vite/index.mjs` applies (memory 029's transform pipeline) — what tests import from `dist/registry` is byte-faithful to what a user's Vite build produces from the copied source. Every style resolves splice-then-inline: `applyStyleVariant(canonical, styleModule, style)` then `inlineTypes(…, typesModule)` — edit canonical + style module + types module, never dist. A component entry missing its conventional style module or types module fails the build with a named error.
  - **`.d.ts` is the splice typecheck gate**: declarations are emitted by `bunx tsc --emitDeclarationOnly` over the staged flavor-resolved sources (splice + types-inline resolved, so staged sources are self-contained and no `-types.js` import survives into dist); a style module that produces non-compiling output fails the build. This is not the canonicals' only typecheck: `tsconfig.lint.json` includes `registry/**`, and each canonical standalone-typechecks through the ambient `declare const` placeholders in its `@hella:styles` region (see §Registry gotchas).
  - **Coverage instruments `dist/registry/**.js`** (bunfig include) — the parity harness imports compiled variants because registry canonicals are never executed under bun test (see §Non-obvious).

  ## Non-obvious

  - **Peers are convention-declared, functionally inert.** `lib/` never imports `@hellajs/*`; the CLI bundles standalone on `node:` builtins plus `esbuild` (below). The peers exist because the COPIED source imports them in the user's project, and `checkPeers` enforces their presence there at add time. Do not "fix" the undeclared-import shape by adding dependencies (memory 023: all-peer convention, carets, zero devDeps — the `clsx`/`tailwind-merge` devDeps are the registry-canonical exception, see §Registry gotchas).
  - **`esbuild` is the package's first and only runtime `dependency`.** `stripTypes` calls its JS API (`transformSync`) at add time; the binary arrives through esbuild's own `optionalDependencies` at install. It is a real dependency, not a devDep, because the published artifact IS the CLI — a devDep would dangle for `bunx @hellajs/ui`. The bundle externals rule (`externalFlags` in `scripts/bundle/esbuild-build.ts`, peerDeps + `dependencies`) keeps the JS API external in `dist` — it must never inline. This supersedes the old "pure `node:` builtins" invariant; `@hellajs/*` peers stay convention-declared. Bun and Deno users need none of this: TS runs natively there, so `--lang js` is only for JS-only toolchains.
  - **The `--lang js` rename map retargets every TS file.** `.tsx` → `.jsx`, other `.ts` (`cn.ts`, `tokens.ts`) → `.js`; `theme.css` passes through verbatim. `stripTypes` runs AFTER `applyStyleVariant` — the splice consumes the `@hella:` markers first, so the stripper never sees a marker line (esbuild would keep them as comments; the contract is that markers never ship). The `ts` path is byte-identical to pre-lang behavior: same renames, no strip.
  - **`import.meta.dir` anchors at the `dist/` root.** Per-module bundling inlines `internal/` imports one level up and the bundle flattens fully, so any runtime form evaluates it at `dist/` (or `lib/`) depth: anchor package-relative paths ONE level up from the file (`loadRegistry.ts`'s `REGISTRY_DIR`). A path anchored for `dist/internal/` depth resolves wrong in every runtime form. The unused `dist/internal/*.js` artifacts are not supported surfaces.
  - **Coverage instruments `dist/bundle.js`** (bunfig include-set), so every public export must be reachable from `lib/index.ts` or it silently escapes measurement. This is why `readConfig` is barrel-exported from `internal/`.
  - **Registry canonicals are never executed in this repo's tests.** Tests import COMPILED `dist/registry/**` output; the `utils/jsx.js` bun preload transforms only test-authored `.tsx` files through the babel pipeline, never registry source. In-repo verification of canonicals is structural (marker integrity, style-module binding) + the transform's byte-shape tests.
  - **A new registry entry is a five-artifact blast radius beyond its own files.** `registry.json` + the `§Registry` table row + `helpers/variants.tsx` are the obvious three artifacts; the two ENUMERATED test lists fail otherwise: `main.test.ts`'s `listComponents()` array and `cli-e2e.test.ts`'s `list` stdout string. All five fail only at full-suite time, not at scoped single-file runs.

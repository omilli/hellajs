# Why

Batched tool harnesses can serve a read from before an edit flush lands. Acting on the stale output means debugging (or worse, "fixing") a problem that does not exist — this run saw `wc -l` report pre-edit totals after line-removal edits succeeded, and `rg` print already-replaced text after a successful three-block edit. Both resolved to green on an immediate re-run. The failure mode is asymmetric: re-running costs one command; trusting the stale read costs a wrong edit.

# Evidence

Verified twice in one session (2026-09-05, local-brain-skills plan set): (1) `wc -l` total 281 immediately after edits that dropped `brain-author/SKILL.md` 68→66 lines — explicit per-file re-run showed 277; (2) `rg 'brain-'` printed pre-replacement text seconds after the edit tool reported "Successfully replaced" — a fresh `sleep 1; rg` run returned exit 1 (clean). Pattern: check result contradicts a reported-successful edit → re-run before reacting.

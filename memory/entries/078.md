# Why

`bun doc-snippets` typechecks package-doc blocks against the real exported types, and narrow prop unions (`CVAPropValue<V, M>`) only accept literal types. Two authoring habits silently widen to `string` and fail the strict tier:

1. `const size = { initial: 'sm', md: 'lg' }; button({ size })` — the const assignment widens `'sm'`/`'lg'` to `string` (no contextual type at the declaration), so the later call fails TS2322 against `'sm' | 'lg'`. Inline the literal in the call — `button({ size: { initial: 'sm', md: 'lg' } })` — so contextual typing keeps the literals narrow.
2. `const size = signal('sm'); button({ size: size() })` — `signal('sm')` infers `signal<string>`, so `size()` returns `string`. Annotate the generic: `signal<'sm' | 'lg'>('sm')`.

Blocks are per-doc nested scopes (see 053 for the module mechanics): a name declared in an earlier block of the SAME doc is visible later, but a name that only exists in a DIFFERENT doc (e.g. a `button` recipe defined in cva.mdx referenced from cx.mdx) is TS2304 — every block must be self-contained within its own doc.

# Evidence

css v3 unit 02 (2026-08-30): writing `packages/css/docs/api/cva.mdx` + `cx.mdx` + `patterns/styling.mdx` produced 4 strict diagnostics on first run — `TS2322 Type 'string' is not assignable to type 'CVAPropValue<…>'` (signal-generic case at cva.mdx:101 and const-widening at patterns styling:28) and `TS2304 Cannot find name 'button'/'isFullWidth'` (cx.mdx:21 referencing a recipe no block in that doc declared). Fixed by `signal<'sm' | 'lg'>('sm')`, inlining the responsive literal at the call site, and making the cx block declare its own `cva()` recipe; `bun doc-snippets` exit 0 (strict tier clean, 0 diagnostics). Units 03–05 of plans/css/code/api-v3 write more variant/prop-typed doc examples and will hit the same two widenings without this.

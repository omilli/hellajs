# Why

`delay()` is the most common test-timing utility, and the tests guide literally says "flush the microtask queue" — but `Promise.resolve()` enqueues exactly one microtask. One hop is enough for a `signal.set(x) → effect()` trip (the reactive graph settles synchronously; the effect callback schedules itself as one microtask), but not for:

- **Multi-hop promise chains.** An already-rejected `.then(f).catch(g)` queues g only after f's rejection microtask — `delay()` lands between the hops (memory 042).
- **Async generator yields.** `for await` resumes the generator on a separate microtask from each `yield` — `delay()` isolates the generator at the yield point, not past its post-yield synchronous continuation (memory 021).
- **GC / WeakRef.** Bun.gc cannot collect objects reachable from scheduled-but-unprocessed async machinery — `delay(0)` (macrotask boundary) drains the pending microtask queue so GC can collect (memory 064).

The fix is universal: when you need to drain beyond one hop, use `delay(0)` (macrotask via setTimeout 0) or `delay(N)` (real-time wait). `delay(0)` is the sanctioned alternative to the banned double-`delay()`.

# Evidence

`utils/test-helpers.js` implementation (verified 2026-08-31): `delay()` → `Promise.resolve()`, `delay(N)` → `new Promise(r => setTimeout(r, N))`, `delay(val, ms)` → `setTimeout(() => r(val), ms)`, `delay(val)` → `Promise.resolve(val)`. No variant is more than one hop.

Memory entries 021 (ssrStream generator yields), 042 (.then().catch() two-hop chain), and 064 (GC macrotask turn) each demonstrate the insufficiency in a specific domain — this entry generalizes the pattern across all of them.

`guides/tests.md` §Async Tests: "Use `delay()` (no args) to flush the microtask queue — equivalent to `await Promise.resolve()`" — the "flush the queue" claim is imprecise. `Promise.resolve()` is one hop. The guide was updated concurrently with this entry (2026-08-31).

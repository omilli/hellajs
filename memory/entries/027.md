# Why

A streaming-SSR example worker (unit 03) found that `curl /users/1` then `curl /` in the same server
process both rendered the `/users/1` view — the second request never re-resolved. The root cause was
`router()` init (`packages/router/lib/router.ts`): it set the route signal's path inside
`if (!route().handler) { route({ ...route(), path: initialPath }); }`, a guard meant to stop a CLIENT
re-init from clobbering the current route. But once the first `router({ url })` resolved and set a
handler, every subsequent `router({ url })` skipped the path update, so `updateRoute()` re-resolved the
stale first path. The router SSR tests (`packages/router/tests/ssr.test.ts`) each call `router()` once
on fresh state, so the sequential case was uncovered — and memory 018 ("router SSR is library
territory, router({ url }) resolves the request URL") asserted the behavior without this trap being
visible.

Recall this before touching `router()` init or building any per-request SSR (isomorphic routing): the
invariant is "an explicit `url` ALWAYS re-resolves against it; the `!route().handler` guard is for
client re-init only." Re-introducing an unconditional guard re-breaks multi-request SSR.

# Evidence

- `packages/router/lib/router.ts` — the init block now reads
  `if (config.url !== undefined || !route().handler) { route({ ...route(), path: initialPath }); }`
  followed by an unconditional `updateRoute()`. The comment documents the SSR-vs-client distinction.
- `packages/router/tests/ssr.test.ts` — "re-resolves the url on each router() call in one process
  (SSR per-request)": `router({ routes, url: "/users/7" })` then `router({ routes, url: "/" })` asserts
  `route().path` becomes `"/"` and each handler fires exactly once.
- `bun coverage router` → 165 pass (was 164), 100% lines, lint green.
- Pre-fix repro: `router({routes,url:'/users/7'})` then `router({routes,url:'/'})` both rendered
  `USER 7` (stale); post-fix the second renders `HOME`.
- Composes with memory 018 (router SSR); does not supersede it.

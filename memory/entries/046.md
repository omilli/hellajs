# Why

Overload resolution selects on the narrowed parameter type (`DocOptions & { body: string }` / `DocOptions & { body: ReadableStream<string> }`). `{}`-as-broad-interface satisfies neither narrowing, so tsc rejects the call before the runtime throw is ever exercised — the test that validated the pre-overload signature no longer compiles against the overloaded one. Casting to ONE concrete overload shape keeps the negative path (runtime `body is required` throw) compilable and covered: the cast lies minimally ("pretend a string body is coming") while `{}` at runtime still trips the guard.

Applies to any negative/invalid-input test (missing option, wrong shape) against a function that has public overloads — dom/router candidates if they gain overload pairs.

# Evidence

- Failure 2026-08-22: `packages/ssr/tests/doc.test.ts:118` — `expect(() => doc({} as DocOptions)).toThrow(...)` → `error TS2769: No overload matches this call. Overload 1 of 2 '(options: DocOptions & { body: string; }): string' … Overload 2 of 2 …` (tsc inside `bun coverage ssr`).
- Fix: `doc({} as DocOptions & { body: string })` — tsc clean, test green, throw covered (`[ssr] doc: body is required, received undefined`).
- `bun coverage ssr` exit 0 after the fix (159 pass, 100.00% lines).

# Why
A `brain-critic` run claimed a settled request's armed `timeout` timer aborts "whichever controller is current at fire time" and therefore kills the next in-flight request — a Break-severity cost asserted from the timer closure capturing the `currentAbortController` variable, without enumerating the transitions. The claim is unreachable: the closure can only observe the dead controller it was created with (harmless no-op) or a successor whose creation already aborted the predecessor (clearing the timer). Assertions about abort wiring must enumerate every controller transition first; narrating a plausible closure shape is not a repro. Ignoring this wastes a plan slot on an unpinnable test (the scenario passes with and without the fix) and erodes trust in Break findings.

# Evidence
`packages/resource/lib/resource.ts` `cleanAbort(controller?)` unconditionally aborts `currentAbortController` before returning `controller ?? new AbortController()`. All four assignment sites route through it: `run` request phase (`cleanAbort()`), the dedup joiner (`cleanAbort(abortController)` — still aborts the prior), `mutate` (`cleanAbort()`), and `abort()` (explicit abort, then `undefined`). The abort fires the predecessor signal's clear-timeout listener — pre-refactor the inline `addEventListener("abort", () => clearTimeout(timeoutId))`; since plan set `critic-fixes` unit 02, the same wiring lives in `wireRequestControls` (`packages/resource/lib/internal/abort.ts`) with a `release()` that additionally clears timers/listeners on every settle path (fixing the real defects: external-`abortSignal` listener accumulation, event-loop retention). Worker correction recorded in `plans/resource/code/critic-fixes/02-request-pipeline.md` §Scope; behavior pinned by `tests/fetching.test.ts` / `tests/prefetch.test.ts` listener-net-zero tests (216 pass / 0 fail, 2026-08-25).

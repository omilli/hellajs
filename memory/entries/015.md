# Why

A streaming-SSR design session decomposed the feature into B (streaming response) + C (streaming/selective hydration) and chose **β** (stream HTML for paint, hydrate once when the stream completes) over **α** (the full React/Vue/Solid selective/streaming-hydration model). The decision rests on HellaJS's hydrate being cheap: α exists in React because React hydration is expensive (it re-runs the component tree and reconciles against the DOM, so deferring/per-segmenting hydration is a real perf necessity), but HellaJS hydrate is a single marker-reader pass that adopts existing DOM with no VDOM and no diff — so β's "hydrate once at stream end" is fast even for large pages, and α's hydrate-core rework buys little. β is also the more reversible choice (hydrate untouched; α reworks `internal/hydrate.ts`'s core). Recalling the rationale prevents re-litigating α-vs-β on future streaming/hydration work and prevents prematurely building α's complexity. α remains a non-committed future option — β's swap points become α's incremental-hydrate hooks if ever needed. Full plan detail lives in `plans/ssr/code/streaming/`.

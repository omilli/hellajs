# Why

A `${infer Param}` slot in a template-literal conditional has no notion of the grammar's `/` delimiter — it matches greedily enough to satisfy the surrounding literals, so a token can span segments. When the trailing literal is just `?` (optional-param form), TypeScript happily infers `Param = "id/:name"` from `"/users/:id/:name?"` — the required-with-slash branch never fires because the optional-at-end branch matched first across the boundary, yielding `{ "id/:name"?: string }` instead of `{ id: string; name?: string }`. Adding a new token form (`:param+`, regex constraints) to a cascade type hits the same trap.

The fix is structural, not a guard: split the pattern into segments first (`PatternSegments<Head>/<Rest>` recursion), then classify each segment in isolation (`SegmentParams<":name?">` → `{ name?: string }`). Inside one segment an `infer` slot cannot cross a `/` because the segment contains none. Optional keys propagate through intersections (`{ id: string } & { name?: string }`), not union-mapped keys (`keyof` + mapped type flattens optionality away — `{ [K in Param | keyof Rest]: string }` would make an optional key required).

# Evidence

`packages/router/lib/types.d.ts` — `ExtractParams` is `PatternSegments`/`SegmentParams` segment recursion (optional-params unit, plans/router/code/behavior-gaps/06). First cascade attempt produced the bogus key: tsc probe on `ExtractParams<"/users/:id/:name?">` errored `TS2353: 'id' does not exist in type '{ "id/:name"?: string }'` (2026-08-31 session). After the segment-recursion rewrite the same probe compiled clean with both `@ts-expect-error` lines (required `id`, required `*`) firing as intended.

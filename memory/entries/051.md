# Why

Core's `signal()` returns a bare closure — no marker property, no brand (packages/core/lib/signal.ts). So inside `createStore`, `initial[key]` being a function means EITHER a preserved user function (plain-object initial) OR a signal (composed initial — every data property of a store object IS a function). `isFunction` therefore cannot discriminate; two separate features broke on exactly this confusion during the 2026-08-25 critic-fixes run:

1. `update()`'s skip guard written as `isFunction(initial[key])` skipped legit leaf writes through composed wrappers — `appStore.update({ user: { name: "Bob" } })` recursed into the inner store whose `initial` is the source store object, `initial.name` is a signal (function), guard fired, write dropped. `nested.test.ts` "update on composed store propagates to nested stores" caught it (the ONLY existing test that would).
2. The snapshot computed's function-preservation branch (`isFunction(originalValue)` → preserve uncalled) captured composed signals uncalled once delegation to nested `snapshot()` actually invoked inner snapshots — returning functions as snapshot leaves AND forming no subscriptions (composed snapshot reactivity dead, 5 tests red).

Both fixed with one mechanism: `createStore` builds a `Set<string>` of signal-backed keys (added in the init pass's signal branch; for composed inputs, function-valued keys are added only when the SOURCE store's registry contains them — composition threads the registry), attached as a non-enumerable symbol property (`settableRegistry`, module-level in `lib/internal/create.ts`). Non-enumerable → invisible to `Object.keys`/`Object.entries`, so snapshots, cleanup walks, `isStore` checks, and `resultKeys` are unaffected. `update()` writes only registered keys (one guard covering unknown + reserved + function keys); the snapshot branch preserves a function only when `isFunction(originalValue) && !settableKeys.has(key)`.

What breaks if ignored: any future store path that re-derives provenance from value shape (`isFunction`, property rewriting, walking `initial`) reintroduces the composed-store break — silently where no composed test covers the path. Rule: need provenance → thread the registry; do not inspect values.

# Evidence

Verified empirically against `@hellajs/store/bundle` (dist imports only — see 050) on 2026-08-25:

- Guard failure: after adding the `isFunction(initial[key])` skip to the update loop, `bun coverage store` failed exactly `nested.test.ts` "update on composed store propagates to nested stores" (`appStore.user.name()` stayed "Alice"); the registry replacement re-greened it (80 pass at that point).
- Snapshot failure: `effect(() => cont.inner.snapshot())` + leaf write → 1 run (dead) with the plain `isFunction(originalValue)` branch; `!settableKeys.has(key)` discriminator → full chain reactive (5 composed reactivity tests green; final 91 pass / 0 fail, 100.00% lines/funcs).
- Registry invisibility: `Object.defineProperty(result, settableRegistry, { value: settableKeys })` — default `enumerable: false`; snapshot resultKeys (`Object.keys(result)`) and cleanup walks unchanged; suite green confirms no enumeration pollution.
- Core signal has no marker: `packages/core/lib/signal.ts` returns a plain `function (value?: T)` closure — nothing to brand-check.

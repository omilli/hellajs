# Why

Migrating hardcoded `class="tag"` strings to the v3 `style()` idiom invites naming the const after the class it generates. But the markup context often already binds that name:

- `ForEach each={tags} use={(tag) => <span class={tag}>}` — the callback param shadows the module const; `class={tag}` binds the loop STRING, not the hashed class.
- `const Tags = ({ tags = [] }) => <div class={tags}>` — the PROP shadows the const, and this one is SILENT: dom's `class` attribute accepts arrays (packages/dom/lib/internal/render.ts:95 `Array.isArray(value)`; ssr mirrors at packages/ssr/lib/internal/serialize.ts:72 "class lists — renderProp joins filtering falsy"), so `class={string[]}` typechecks and renders the raw strings as class names. No error, wrong classes.

Fix pattern (examples/blog/src/components/Tags.tsx, unit 04): rename the const, keep the prop/param API — `const tagList = style({...}, { label: "tags" })` consumed as `class={tagList}`, callback param renamed `t`. The `label` keeps the generated class readable; the const name only matters in markup scope.

# Evidence

- Hit twice in one file during unit 04 (2026-09-03): first the `use={(tag: string) => ...}` param shadow, then the `({ tags = [] })` prop shadow — the second survived the first fix and would have shipped `class={["react","vue"]}`-shaped output.
- Array acceptance verified from source this session: render.ts:95 (client renderProp) and serialize.ts:72 (server serializeProp) both branch on `Array.isArray` for class lists — the prop case cannot be caught by tsc.

# Why

The gap flagged in `packages/store/store-comparison.md` §6 ("no per-element array reactivity") originated from an agent readiness-assessment of that doc, NOT from a user issue, example, or a stated competitive-parity goal. Tracing the actual capability collapses the motivation:

- The headline "1000-row table" rendering case is already solved at the view layer. `ForEach` (`packages/dom/lib/ForEach.ts`) does keyed LIS reconciliation in one effect that reads the array signal, and the documented pattern (`packages/dom/docs/api/foreach.mdx:126-144`) puts signals *inside* items — DOM work is surgical regardless of store-level granularity.
- The only behavior not otherwise deliverable is granular *non-rendering* derived effects over large arrays (an effect reading `s.items()[i].field()` that should not wake on sibling writes). Narrow workload, zero demonstrated demand.
- Option D (composition: `store({ rows: [store({...}), ...] })` + snapshot/readDeep/applyUpdate/cleanup rework) was the chosen build mechanism if pursued. It is reversible — re-plan when a real user need surfaces, not before.

Build cost is disproportionate: snapshot flatten + row-store cleanup + `applyUpdate` reconcile-by-index + a recursive `UnwrapArrays<T>` type conditional + granularity-matrix docs, plus a stores-vs-signals discriminator sharp edge (the mechanism keys on `isStore`; an array of signals would NOT trigger it). The honest HellaJS position is the no-proxy construction-time model — granular property signals without per-access interception. Per-element reactivity IS available today via composition for direct writes (shared signal refs = granular); the snapshot/draft/cleanup limitations of that path are real and should be documented honestly, not used to justify a build.

# Evidence

Verified against source 2026-07-03:

- `packages/store/lib/internal/create.ts` — `createStore` init loop falls through to `signal(value)` for arrays; `snapshotComputed` `isFunction(value)` branch returns raw array (store refs, not plains) for array-of-stores; `deepCleanup` skips signal/function values → leaks row stores.
- `packages/store/lib/internal/draft.ts` — `extractChanges` array branch rewrites object-element arrays wholesale (deepClone breaks `===`).
- `packages/store/lib/internal/utils.ts` — `applyUpdate` blind-sets the signal; `isStore` discriminator (snapshot/update/cleanup own-properties).
- `packages/store/lib/types.d.ts` — `Store["snapshot"]: () => T` lies for array-of-stores inputs (claims to return stores).
- Composition confirmed broken in 4 places today (snapshot, draft, mixed plain/store writes, cleanup).
- View coverage: `packages/dom/lib/ForEach.ts` (keyed LIS), `packages/dom/docs/api/foreach.mdx:126-144` (inner-signals pattern). Cross-module: zero `.snapshot()` consumers outside `packages/store/`.

User decision to dissolve: explicit, this session. Dissolved plan artifact: `plans/store/code/per-element-array-reactivity.md`.

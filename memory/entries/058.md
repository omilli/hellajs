# Why

The stale-index bug (057, now archived): `removeRule` deleted by stored numeric index, `deleteRule(i)` shifts every later rule down one, and nothing rebased — multi-rule `removeCss` leaked trailing rules and any removal after an earlier removal silently no-opped (out-of-range `deleteRule` threw into the silent catch). Fixed at the single choke point:

- `rebaseIndexes(qid, removedIndex)` decrements every `${qid}:`-prefixed entry above the removed index — prefix-scoped by the qualified sheet key so the other sheet id (`hella-css` vs `hella-vars`) and other hosts never shift.
- `removeRule` rebases after every successful `deleteRule`; a **throwing** `deleteRule` shifted nothing — its catch path correctly skips the rebase. Don't add one there.
- `upsertRule`'s update path rebases a platform-rejected re-insert iff its preceding `deleteRule` succeeded (the delete left a hole the failed insert never refilled). That guard is unreachable via the public API under happy-dom — no bucket/rule key's text can flip accepted→rejected through `css()`/`cssVars()` inputs — and is the sole uncovered line the fix added (bundle lines 82–83 = guard + the update-catch `console.warn` already uncovered at baseline; `bun coverage css` 99.61% is expected, not a regression).

Consequence for the containment decision: hosted sheets being one `<style>` per sheet id per host is no longer a correctness necessity — a shared-per-host sheet's index space would now stay exact across css/vars removals. The per-id split remains the shipped architecture (it mirrors the document-path two-element split); switching to shared-per-host is a separate, unbuilt decision.

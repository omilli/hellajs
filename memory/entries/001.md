# Why

A `lib/internal/core.ts`-style shim that re-exports symbols from an external peer dep (e.g. `@hellajs/core`) is NOT pure indirection at the bundle level. esbuild treats each source-file `import { ... } from "<external>"` as a distinct binding declaration and emits it verbatim into the bundle for externals; it does not cross-file merge them, and terser minification does not either. So N consumer files importing directly from an external module yield N import statements in `bundle.js`; routing them through one shim yields 1 import per shim `export {}` statement. Deleting the dom shim would have scaled bundle imports from 1 to ~9 (one per consumer), inflating the bundle and adding redundant module-level bindings. The shim is a real dedup choke point.

# Evidence

Verified empirically 2026-06-29 via a minimal esbuild repro (3 consumer files, `--external:@hellajs/core`):

- no shim, `--minify`: 3 `from"@hellajs/core"` lines in output
- single-statement shim: 1 line

Real artifact: `packages/dom/dist/bundle.js:6-17` shows the current shim emitting one `import { ... } from "@hellajs/core"` line into the bundle. Shim source: `packages/dom/lib/internal/core.ts`.

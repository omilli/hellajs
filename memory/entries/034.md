# Why

The Progressive-Suspense unit (memory 033) shipped a hydrate-integration test asserting `container.querySelector("#root b")!.textContent === "resolved"`. That passed green. But `$hs`'s first version omitted a marker wrapper, so hydrate re-evaluated the Suspense getter → a fresh Promise → stringified to `[object Promise]` appended as a text node directly adjacent to the `<b>resolved</b>` element. The targeted `querySelector("#root b")` found the `<b>` (correct) and read its text (correct) — completely blind to the stray `[object Promise]` sibling. The bug only surfaced when the user ran it in a real browser ("the dom fill [object Promise] next to each card").

The lesson generalizes beyond this one bug: any hydrate/render/swap path that *resolves a child value* (getter → value → node/text) can silently produce a stringification artifact (`[object Promise]`, `[object Object]`) co-located with correctly-rendered content. A querySelector targeted at the expected node will not see it. So hydrate/swap tests should assert on the **full container** — `container.textContent` (and/or an explicit `not.toContain("[object Promise]" / "[object Object]")`, and/or a scan of text-node siblings) — not just a queried element's text.

# Evidence

- `packages/ssr/tests/hydrate-integration.test.ts` — the original test "hydrate swaps a streamed <Suspense> via the fallback…" asserted only `#root b` textContent; it passed while the bug was live.
- `packages/ssr/tests/ssr-suspense.test.ts` — the regression test added ("$hs swap + hydrate adopts the resolved content without stringifying the getter's Promise") asserts `container.textContent.not.toContain("[object Promise]")`; PROVEN to fail without the marker-wrapper fix (temporarily removed the wrapper → `container.textContent` started with `[object Promise]`).
- Friction: the wrong conclusion ("dom needs no change") was drawn from the green-but-insufficient test; the browser caught it. Recalling this prevents re-deriving a false "verified" from a too-narrow hydrate assertion.

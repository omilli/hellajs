# Why

`afterMount` and descendant `isMounted` are set in exactly one place: `processMountQueue` (`lib/internal/queue.ts`). The scoped `MutationObserver` does NOT rescue the initial attach, because `registerContainer(container)` runs AFTER `container.replaceChildren(...)` in `mount()` (`lib/mount.ts` attach) — so the observer is blind to the tree it just built — and `hydrate()` adds nothing (the DOM already exists). Before this fix, `afterMount` never fired and nested `beforeUpdate`/`afterUpdate` were permanently dead unless the user called `handle.flush()` — contradicting the `mount` docs, which framed `flush()` as optional ("useful for tests and synchronous access"). `plugins/astro/client.mjs` never flushed, so every Astro island silently lost `afterMount` + nested update hooks.

Resolution: `mount()`/`hydrate()` now call the handle's `flush()` as the final statement of `attach()`, so `afterMount` fires by the time they return — **no user `flush()` required**. Three load-bearing details, each a footgun if ignored:

- **Idempotency.** `processMountQueue` skips already-`isMounted` descendants (`if (state.isMounted) return;`), so a later `handle.flush()` (or an observer re-fire on a moved node) never double-fires `afterMount`. Safe because `cleanupSubtree` → `deleteState` (`lib/internal/cleanup.ts:62`), so a genuinely re-mounted node gets fresh `isMounted=false` and fires once.
- **`addHook` immediate-fires.** `registry.addHook(element, "afterMount", fn)` fires `fn(element)` immediately when the node is already `isMounted`. This centralizes (and replaces) the inline check `createReactive.hooks` used to carry (`lib/internal/reactive.ts`), and is what makes a post-mount `addHook(afterMount)` work without relying on `flush()` re-firing. During the walk `isMounted` is always false, so this never fires early for tree-declared hooks.
- **Root included.** `traverseDescendants` visits the node itself (stack seeded with `[node]`), so the root's `isMounted`/`afterMount` are set by `processMountQueue`. The old inline `getState(root).isMounted = true` in `attach()` was removed — keeping it would have made the idempotency guard skip the root's `afterMount` entirely.

What breaks if ignored: re-introducing an inline root-`isMounted` set, removing the idempotency guard (double-fire across every existing `flush()` caller), or moving the immediate-fire back out of `addHook` (post-mount hooks go dead again).

# Evidence

Verified empirically (probe test, since deleted): without `flush()`, `afterMount`=0 and nested `afterUpdate`=0 for BOTH `mount` and `hydrate`, even after microtasks settle; with `flush()`, both=1. Source: `lib/internal/queue.ts` `processMountQueue` (sole writer of descendant `isMounted` + sole `afterMount` runner); `lib/mount.ts` & `lib/hydrate.ts` `attach()` (internal `flush()` call); `lib/registry.ts` `addHook` (immediate-fire); `lib/internal/state.ts` (`isMounted: false` initial shape); `lib/internal/cleanup.ts:62` (`deleteState`). Gate: `bun coverage dom` → 329 pass / 0 fail; `bun lint` → tsc + eslint + 4 guards clean. Regression test for the idempotency guard: `registry.test.ts` "explicit flush() after mount does not re-fire afterMount".

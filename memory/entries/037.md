# Why

Two layers must agree for reactivity, and before 2026-08-09 they diverged for attributes:

1. **Runtime gate** — `render.ts` `mountNode` props loop: `if (!isFunction(value)) { renderProp(...); return; } registry.addEffect(...)`. The *only* thing that makes an attribute (or child) reactive is the value being a function. A primitive, an array, or an object renders once and never updates.
2. **Compile layer** — babel `maybeReactive` (`src/utils/reactive.mjs`, `containsCall` recurses via babel `VISITOR_KEYS`) wraps a call-containing expression into `() => expr` so it passes the runtime gate. It is a safe no-op when there is no call (static strings, numbers, bare identifiers, member-chains-without-calls pass through), and its top-level-function guard prevents double-wrapping an explicit `() => …`.

Before this change `maybeReactive` was applied to **children only**, so call-containing **attributes** (`class={signal()}`, `class={[signal(), "x"]}`, `class={cond() ? "a" : "b"}`) compiled to a raw value/array → `isFunction` false → rendered once, never updated. `dom-comparison.md:35` claimed "`{signal()}` is reactive" — true for children, silently false for attributes. The fix extended `maybeReactive` to element attribute values (props branch only, gated `!isComponent`), aligning the two layers; the runtime needed **no change** because `renderProp` (`utils.ts`) already joined arrays via `filter(Boolean).join(" ")` and the `isFunction` effect already re-ran on signal change.

Recall this before: editing attribute/child reactivity, debugging "why doesn't my attribute update on signal change", reasoning about runtime-vs-compiled `html\`\`` reactivity, or touching the `isFunction` gate in `render.ts`/`reactive.ts`. The signal-ref-vs-called distinction (`{signal}` reactive by virtue of the signal being a function; `{signal()}` reactive only because the compiler wraps it) is the single most common confusion.

# Evidence

- `packages/dom/lib/internal/render.ts` `mountNode` props loop — the single attribute-reactivity gate: `if (!isFunction(value)) { renderProp(element, key, value); return; } registry.addEffect(element, () => renderProp(element, key, value()))`.
- `packages/dom/lib/internal/reactive.ts` `bind` — same `isFunction(val) ? registry.addEffect(...) : set()` gate for `$ref`/`$collection`.
- `packages/dom/lib/internal/utils.ts` `renderProp` — `if (Array.isArray(value)) element.setAttribute(key, value.filter(Boolean).join(" "))`; already handled wrapped arrays (zero runtime change for the feature).
- `plugins/babel/src/utils/reactive.mjs` — `maybeReactive` + `containsCall`.
- Application sites (all gated `!isComponent`): `plugins/babel/src/processors/children.mjs` (JSX element children); `plugins/babel/src/processors/attributes.mjs` `processAttributes` props branch (JSX element attribute values, prefixed keys excluded); `plugins/babel/src/builders/ast.mjs` `processComponentAttributes(..., isComponent)` `__slot` + `Array.isArray` branches (compiled `html\`\`` element children + attributes).
- Excluded by construction: component branches (`isComponent=true`), prefixed keys (`on:`/`e:`/`hook:`/`error:` routed before the props branch), double-wrap guard (top-level function).
- Probe this session (babel transform output): `<div class={signal()} />` → `class: () => signal()`; `<div class={[signal(), "x"]} />` → `class: () => [signal(), "x"]`; `<div on:click={handleClick()} />` → `on: { click: handleClick() }` (unwrapped); `<Btn class={fn()} />` → `class: fn()` (component, unwrapped); html`` `<${Comp} class="${fn()}">` → unwrapped.
- `packages/dom/lib/html.ts` `cloneWithValues` — runtime `html\`\`` interpolates raw values; cannot inspect/wrap.
- Tests: `bun test plugins/babel/tests` 225 pass (8 new compile-shape cases incl. component/prefix exclusion); `bun coverage dom` 339 pass (3 new runtime tests: reactive array attribute, reactive call attribute, re-filter on update), coverage 98.88% funcs / 98.03% lines, lint green.

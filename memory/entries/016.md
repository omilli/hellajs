> **Naming superseded 2026-08-22 (entry 045):** `ssrAsync`→`ssr.async`, `ssrStream`→`ssr.stream`, `docStream`→`doc` (stream overload) — the old names below are the pre-v2 API, kept for history.

# Why

Hit twice while writing async-SSR tests. The first time it shipped as a real coverage drop: an `ssrAsync` rejection test written as `expect(ssrAsync(...)).rejects.toThrow("boom")` (no `await`) passed, but the rejection code path (`controller.error`/propagation) stayed uncovered — `bun coverage` showed the lines uncovered and I re-derived the cause mid-run. Adding `await` made the assertion actually settle, covered the path, and restored 100%. The second time (a stream test) I preempted it. Recalling this prevents both the silent false-pass (a "rejection test" that doesn't test rejection) and the mystery coverage drop on async error paths.

The general rule: any matcher that returns a Promise — `.rejects.*` and `.resolves.*` — must be `await`ed (or returned) so the test waits for the assertion. This is a bun:test/Jest-family footgun, not HellaJS-specific, but it bites wherever async error handling is tested (resource rejections, ssr/ssrStream error propagation, Lazy `.catch`, error-boundary dispatch).

# Evidence

- `packages/ssr/tests/ssr-async.test.ts` — `propagates a rejected Promise to the caller` test: `await expect(ssrAsync(html\`<p>${() => Promise.reject(new Error("boom"))}</p>\`)).rejects.toThrow("boom");`. Without the leading `await`, `bun coverage ssr` showed the rejection path uncovered; with it, 100%.
- `packages/ssr/tests/ssr-stream.test.ts` — same pattern, `await expect(collect(ssrStream(...))).rejects.toThrow("boom")`.
- Confirmed 2026-07-12 during the ssrAsync/ssrStream build (`plans/ssr/code/async-ssr/`, `plans/ssr/code/streaming/`).

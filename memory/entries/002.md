# Why

`resourceCache.prefetch` stores its result via `setCacheData(fetcher, key, result, cacheTime, staleTime ?? Infinity)`. The `?? Infinity` coalesce is load-bearing, not decorative: it matches `resource()`'s `staleTime` default so the cached entry is never stale. A later `resource(fetcher, { key, cacheTime })` then cache-hits and returns immediately WITHOUT firing SWR (background refetch).

Passing the raw `staleTime` option instead lets `setCacheData` default it to `0` (always stale). The resource's cache phase then sees a stale entry and triggers a background `run(true)`, re-calling the fetcher — silently breaking the "prefetched entry is reused, fetcher not re-called" contract. The prefetch plan's Strategy prose wrote `setCacheData(..., staleTime)` without the coalesce; deviating to `?? Infinity` is the intentional fix. Do not "correct" it back to the literal Strategy.

# Evidence

- `packages/resource/lib/cache.ts` prefetch: `setCacheData(fetcher, key, result, cacheTime, staleTime ?? Infinity)`.
- `packages/resource/lib/cache.ts` `setCacheData(scope, key, data, cacheTime = 0, staleTime = 0)` — `staleTime` defaults to `0` when undefined.
- `packages/resource/lib/resource.ts` `run()` cache phase: SWR fires when `isStale(entry) && revalidateOnStale`; `isStale` is true when `staleTime !== Infinity && now - timestamp > staleTime` — i.e. a `staleTime: 0` entry is always stale.
- Guarded by `packages/resource/tests/prefetch.test.ts` "prefetched entries are reused by a resource sharing the fetcher reference" → `expect(fetcher).toHaveBeenCalledTimes(1)` (fails if SWR refetches).
- `bun coverage resource` → 188 pass, exit 0.

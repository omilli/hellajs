# Why

The server-side css state leak (module-level maps accumulating across requests) was the hardest problem in the SSR track. Six approaches were investigated and rejected before arriving at platform-dependent return:

1. ssr imports css, calls resetCss internally → coupling (users without css break)
2. ssr decoupled, caller drains manually via resetCss → works but leak footgun
3. collectCss (emitter pattern, callback wrapper) → user rejected compound return (HTML+CSS bundled)
4. ssr owns its own non-reactive css → "two css functions feels off"
5. css() returns text always (unified, breaking) → breaks cssVars reactivity (pure function can't set up effects)
6. Platform-dependent return (text on server, name on client) → PRESERVES cssVars (client path untouched), stateless on server, zero coupling

The key insight: css()'s return value doesn't need to be the name on the server because the name is an INPUT (the user provided it via `{name:"btn"}`). The server returns the text; the user already knows the name. Components hardcode class names. CSS lives in shared modules, not inline in component templates.

The `<style>` transform removal follows: the transform assumed css() returns a name usable as a class. Under platform-dependent return, that breaks on the server. Removing the transform means users call css() explicitly — they control the return value per platform. Also makes JSX and `html\`\`` handle `<style>` consistently (both as regular elements).

Rejected alternatives for text retrieval: manual drain (leak footgun), collectCss (compound return), text-return-unified (breaks cssVars).

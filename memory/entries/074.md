# Why

The `\w+` after `typeof` only matches bare identifiers. Real sites also apply typeof to `member.expression`, `arr[0]`, and `(value as T).prop` — all invisible to the regex but all flagged by eslint's selector `BinaryExpression[operator=/^[=!]==?$/] > UnaryExpression[operator='typeof']`, which matches any UnaryExpression typeof operand regardless of its inner operand shape. Consequences when the two disagree:

- A plan whose Files/citation list derives from the `\w+` grep under-scopes the conversion; executing it verbatim leaves `bun lint` red once the ban lands (the ban catches what the grep missed).
- Conversely, forms that deliberately stay raw are invisible to BOTH: factored discriminant locals (`const t = typeof child` then `t === "string"` — template.ts's parse hot loop reads typeof once, compares thrice) and `switch (typeof x)` discriminants. That is by design — prose-enforced, not lint-enforced.

So: discovery/audit = bare `rg -n "typeof" packages/<pkg>/lib --glob '!dist'` + eyeball each hit into convert / stays-raw / type-position / message-arm; the eslint run is the enforcement check, not the discovery tool.

# Evidence

Verified 2026-09-01, plans/core/code/type-guards unit 03: the plan's DoD grep returned zero hits over dom while `rg -n "typeof" packages/dom/lib` still showed render.ts:229 (`typeof children[0]`), mount.ts/hydrate.ts thenable checks (`typeof (resolved as { then?: unknown }).then`), Suspense.ts:21,83 (`typeof (value as Promise<unknown>).then`) — all converted, all would have failed unit 07's `bun lint` gate if left. Unit 07 probe confirmed the selector fires on `typeof x === "string"` (probe exit 1) while template.ts:249's factored form passes it by design.

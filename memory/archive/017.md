# Why

A router-SSR design session (SSR gap #1) first converged toward a `resolveRoute(config, url)` server-side resolver in `@hellajs/router`. The user's challenge — "why have router SSR at all if servers handle routes already?" — overturned it. The collapse rests on three reasons, all about **worth, not capability**:

1. **Servers route.** URL→component is the server's job (Bun `fetch`, Express, Hono, a worker). A `resolveRoute` duplicates it.
2. **The universal library/meta-framework split.** Verified against `@solidjs/router`'s README: Solid's router SSR is isomorphic (`<Router url={isServer ? req.url : ""}>`, same component server+client) AND paired with **SolidStart**, which owns `entry-server.tsx`, request-scoped data (`cache()` "does deduping on the server for the lifetime of the request"), streaming, and build presets. The pattern is industry-wide: `react-router` (StaticRouter)→Next/Remix; `vue-router` (memory history)→Nuxt; `@solidjs/router`→SolidStart. **None ships router SSR as a standalone library feature that replaces the server.** HellaJS has no meta-framework layer, so a standalone `resolveRoute` is one orphan primitive from that layer — the user still wires the server.
3. **Renderer identity (Crux 1).** Even granting env-agnostic primitives, HellaJS's `ssr` reads current values once by design (runs no effects), so Solid's "pass `url` to `<Router>`, reactivity renders it" isn't HellaJS's render path anyway. Isomorphic routing wouldn't make the server render reactive; it'd just be setup-before-a-one-shot-read.

The shared-routing value (one route tree, no server/client drift, guards/redirects once, hydration agreement) is real but meta-framework-scoped: worth building **holistically** (routing + request-scoped data + streaming + build) IF/WHEN HellaJS becomes a meta-framework (the user's "not a meta-framework *yet*"), not speculatively as a library primitive now. Building `resolveRoute` in isolation today would likely get redesigned when the meta-framework takes shape.

**Corrected fact (do not re-conflate).** This session's first router-SSR argument claimed "Solid's stack is isomorphic, HellaJS's isn't, so isomorphic routing doesn't transfer." That conflated two things: `ssr` not *subscribing* to reactivity (a true renderer property) with the *primitives* not being isomorphic (false — `signal`/`computed`/`effect` are env-agnostic, zero DOM refs, memory 005). The env-agnostic primitives make isomorphic routing more *feasible*, but not more *worth it* as a standalone library feature (servers still route; the value is meta-framework-scoped). The accurate comparison point — Solid runs its reactive runtime *during the render*, HellaJS's `ssr` reads once and runs no effects — is already in `ssr-comparison.md` §2 and is a comparison fact, not a router-SSR decision driver.

# Evidence

- `@solidjs/router` README (verified via raw.githubusercontent.com 2026-07-12): "SSR Routing: For SSR you can use the static router directly or the browser Router defaults to it on the server, just pass in the url" → `<Router url={isServer ? req.url : ""} />`; `cache()`/`action()` "does deduping on the server for the lifetime of the request" (the request-scoped data mechanism async SSR needs).
- SolidStart README: `entry-server.tsx` "Manages server-side request handling"; sync/async/stream SSR modes; build presets (Node/Bun/Deno) — the meta-framework layer the router pairs with.
- `packages/ssr/ssr-comparison.md` §2: Solid/React/Vue evaluate client reactivity during the server render; HellaJS's `ssr` reads current values once, running no reactive machinery — the accurate comparison fact (a renderer distinction, not a primitive-capability one).
- `packages/core/lib/index.ts`: exports `signal`/`computed`/`effect`/`batch`/`untracked`/`scope` + `hasWindow`/`hasDocument`/`hasNavigator` *probes* (env-agnostic; memory 005 confirms core/store zero DOM refs). The primitives ARE isomorphic; the RENDERER (`ssr`) chooses not to subscribe.
- Consistent with the same session's Crux 1 (affirm HellaJS's explicit/minimal SSR design): #3/#4/#5 closed as docs for the minimal-pole reason; #1 closes as docs for the meta-framework-scope reason; #6 (selective hydration) stays deferred (memory 015). All eight SSR gaps categorized — features: #2 (`doc`), #7 (error docs), #8 (example); docs: #1, #3, #4, #5; deferred: #6.
- No `resolveRoute` plan was ever written — #1 stayed in `brain-idea`; its only doc deliverable is a server-routing pattern recipe (server routes → `ssr()` → client `router()` + `hydrate`), folded into patterns docs, not a new library API.

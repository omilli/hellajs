# Why

`indexMap` (packages/css/lib/internal/sheet.ts) maps rule keys to **numeric** `cssRules` indexes captured at `insertRule` time. `CSSStyleSheet.deleteRule(i)` shifts every rule after `i` down one — no code rebases the stored indexes, and the shifts are invisible because the affected `deleteRule`/`insertRule` out-of-range calls throw into silent catch blocks. Two concrete failure shapes:

- **Multi-rule leak** — `removeCss` removes split rules in ascending stored-index order (`removeCss.ts` loop `0..ruleCount-1`); after the first `deleteRule`, every remaining stored index is one too high, so it deletes the wrong rule or throws out-of-range (caught) and the entry is dropped with the rule still in the sheet.
- **Cross-text corruption** — removing text A (injected first) shifts text B's stored indexes; B's later `removeCss` no-ops entirely (out-of-range delete throws → caught → entry dropped).

Existing tests never fire it: every removal scenario uses a single-rule object (`css.test.ts` "removes styles", "removeCss preserves styles until all references gone", "removeCss with global styles"). The same staleness applies to vars buckets sharing the `hella-vars` sheet (sequential bucket removals) and to `upsertRule`'s update path when a re-insert is platform-rejected (the successful delete leaves a hole the failed insert never refills).

**Containment decision (style-host unit, 2026-08-30):** hosted sheets are one `<style>` **per sheet id** per host (`Map<string, WeakMap<ParentNode, CSSStyleSheet>>` in `internal/sheet.ts`), NOT the one-shared-sheet-per-host sketch — sharing would let a css removal shift a vars rule's index and corrupt the sibling API's rules on the hosted path. The default path is immune only because `hella-css` and `hella-vars` are separate elements. Revisit (shared-per-host becomes viable) only after an index-rebasing fix lands; fix scoped at `plans/css/code/sheet-internals/remove-rule-stale-index.md`.

# Evidence

- Source: `packages/css/lib/internal/sheet.ts` `removeRule` (deletes by stored index, catch swallows the out-of-range throw, no rebasing) and `upsertRule` update path (`indexMap.set` only on successful insert — clean entry, but no rebase of the hole a rejected re-insert leaves); `packages/css/lib/removeCss.ts` ascending removal loop.
- Empirical repro (bun 1.3.3, `--preload ./utils/happydom.js`, 2026-08-30): `css({color:"red","&:hover":{color:"blue"}},{name:"a"})` → `removeCss(same)` → sheet still holds `.a:hover{color:blue}`. Interleaved: `css(a-name)+css(b-name)` → `removeCss(a)` leaves `.a:hover` AND shifts `.b`; `removeCss(b)` then removes nothing.
- All 145 pre-existing css tests green under the bug (single-rule removal objects only); full repro commands preserved in the style-host plan ticks (`plans/css/code/behavior-gaps/style-host.md`, Code deviation note).

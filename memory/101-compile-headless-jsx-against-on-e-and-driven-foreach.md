# Why

Two snippet patterns that appear in older package docs do not survive compilation, and copying them verbatim into demos or examples produces silently inert handlers or hard runtime throws. A plain `on*` attribute (`onSubmit={...}`) compiles to a literal element attribute, not a listener - it is a reactive prop invoked once at mount and never on the event; only `on:` (delegated) and `e:` (direct) prefixed keys wire events. And `ForEach` reads `props.use` for its render function: the compiler passes function children as `props.children` and never maps them onto `use`, and `keyBy` is not a `ForEachProps` member (props are `each`/`use`/`key`) - so `<ForEach each={x} keyBy="v">{(item) => ...}</ForEach>` throws `[dom] ForEach: use must be a function` at runtime in the browser AND during server prerender.

# Evidence

Verified 2026-11-01 against source and a running build. `plugins/compiler/src/processors/attributes.mjs` routes only `error:`/`hook:`/`e:`/`on:` prefixed keys to event wiring; every other key falls to the plain-attribute branch. `packages/dom/lib/ForEach.ts:50` throws on non-function `props.use`; `fn.ssr = { kind: "forEach", props }` feeds the same props to the server renderer. `packages/dom/lib/types/nodes.d.ts` `ForEachProps` declares `each`/`use`/`key` only. Repro: prerendering a docs page whose island used the function-child form failed with `[dom] ForEach: use must be a function` (astro build error on `/headless/combobox`); switching to the driven `<Combobox.List items={items} keyBy="value" />` form (the component renders ForEach internally with the correct contract) and `on:submit={...}` for the form controller's submit handler passed a 42/42 Playwright probe with zero console errors. Known carriers of the stale patterns as of that date: `packages/headless/docs/api/combobox.mdx` Basic Usage (function-child ForEach), the `combobox()` JSDoc in `packages/headless/lib/combobox.tsx` (same), and `packages/headless/docs/api/form.mdx` Basic Usage (`onSubmit`). `style()` labels embed as `{label}-{hash}` class names, so probe selectors must not expect the bare label. The same hygiene applies to part attributes: not every factory renders a semantic attribute a probe might assume from its props API - `select()` options render `data-value` (no `value` attribute) and `tabs()` triggers carry their value only through the value-derived `hella-tabs-tab-<value>` id - so select parts by the attributes the source actually renders (verified 2026-11-01 against `packages/headless/lib/select.tsx` and `tabs.tsx`), and match the part itself with one exact selector rather than chaining a descendant lookup off the part's own locator.

# Why

A conditional region (`{() => open ? <div hook:afterMount .../> : null}`) inserts its subtree with plain `insertBefore`, and the scoped container observer's additions loop (`packages/dom/lib/internal/queue.ts`, the `addedNodes` handler calling the hooks feature's `collectAdded` arm) queues the inserted root for the mount-queue drain - so `hook:afterMount` on region-inserted nodes DOES fire, via the drain's walk, one microtask after the flush. This corrects the older claim that region inserts never get a walk: the walk reaches them through the observer, not through the reactive region itself.

The hazard is ordering. The compiler wires attributes in source order: a reactive attribute (`data-state={fn}`, `style={fn}`) creates its registry effect via `addEffect` BEFORE a `hook:afterMount` written below it registers. If that effect re-runs in the window between the node's insertion and the mount-queue drain - the classic trigger: a two-signal open handler whose first flip rebuilds the region synchronously (propagation is synchronous) and whose second flip re-runs the freshly created effect on the now-connected node - `runEffectHooks` (`packages/dom/lib/features/hooks.ts`) takes its lazy branch (`!isMountInFlight() && (state.isMounted = el.isConnected)`), marking the node mounted. The drain's walk then hits the idempotence gate (`r.isMounted || (r.isMounted = !0, r.hooks && ...)`) and skips the afterMount: the wiring (a util like `modal`, listeners, disposers) silently never runs, with no error. The guard documented against the hydration flavor of this race does not cover the island-update flavor.

Contract for component-island authors: on any element carrying `hook:afterMount`, place the hook attribute above every reactive attribute; when a click handler both flips a signal read by the mounted subtree and mounts the subtree, flip the subtree-read signal first. With the hook registered first, the effect's creation run sees `state.hooks` already present while the node is still disconnected, so the lazy write records `false` and the drain fires the hook normally; post-walk re-runs only trigger the update brackets.

# Evidence

Live-site bisection against an astro preview of a fresh docs build: with the reactive attr above the hook, a registry-trace probe showed `addHook(afterMount) connected=false` then no fire, while the single queued drain ran without error; reinstalling the hooks feature with the lazy write neutered made the same hook fire, and a faithful replica reproduced the cancellation with the `beforeUpdate` bracket log (`isMounted=true conn=true`). With the attribute order inverted (hook first) plus the arm-before-mount signal order, the full 9-page island probe passed 41/41 with zero console errors. Source read this session: `packages/dom/lib/features/hooks.ts` (`addHook` immediate branch, `runEffectHooks` lazy write, `processMountQueue` walk), `packages/dom/lib/internal/queue.ts` (observer additions loop, arm), `packages/dom/lib/runtime.ts` (`gt` reactive-attr effect, `et` region insert), `packages/dom/lib/registry.ts` (`addEffect`).

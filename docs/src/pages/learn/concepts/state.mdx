# State

State in HellaJS ranges from simple signal-based local state to complex store-based application state.

## State With Signals

[`signal`](/reference/core/signal) provides the foundation for all reactive state. Use signals directly for local component state or global shared state.

### Component State

Encapsulate state within components using signals. Each signal is independent: only the values that change trigger re-renders.

```jsx
import { signal } from '@hellajs/core';

const Counter = () => {
  const count = signal(0);
  const isVisible = signal(true);

  return (
    <div>
      <h1>{count}</h1>
      <button on:click={() => count(count() + 1)}>+</button>
      <button on:click={() => isVisible(!isVisible())}>
        Toggle
      </button>
      {isVisible() && <p>Count is visible</p>}
    </div>
  );
};
```

### Global Shared State

Signals declared in module scope are shared across all components that import them. Combine with [`computed`](/reference/core/computed) for derived values.

```typescript
import { signal, computed } from '@hellajs/core';

const user = signal(null);
const theme = signal('light');

const isLoggedIn = computed(() => !!user());
```

## State With Stores

A [`store`](/reference/store/store) converts a plain object into deeply reactive state where each property is an independently reactive [`signal`](/reference/core/signal). Only the specific properties that change trigger re-computation.

### Creating Stores

```typescript
import { store } from '@hellajs/store';

const counter = store({
  count: 0,
  step: 1,
  guards: {
    min: 0,
    max: 10
  }
});

// Each property is individually reactive
counter.count();        // 0
counter.step();         // 1
counter.guards.max();   // 10

// Set individual properties directly
counter.count(5);
counter.step(2);
```

### What Stores Provide

Beyond basic get/set, stores offer several capabilities, each documented in detail in the [`store`](/reference/store/store) reference.

- **[Readonly](/reference/store/store#readonly-options)**: Restrict specific properties or the entire store to read-only access, enforced at the type level.
- **[Snapshots](/reference/store/store#snapshot)**: Get a plain object representation of the entire store state. Reactive: recomputes when any property changes.
- **[Updates](/reference/store/store#update)**: Apply partial deep merges or mutate a draft directly for ergonomic multi-property and array changes.
- **[Middleware](/reference/store/store#middleware)**: Validate and transform values before they're stored. Runs synchronously on every set operation.
- **[Nested stores](/reference/store/store#nested-stores)**: Compose stores hierarchically. Nested stores share signal references bidirectionally.
- **[Batching](/reference/core/batch)**: Wrap multiple store updates in a [`batch`](/reference/core/batch) to defer computation until all changes are applied.
- **[Cleanup](/reference/store/store#cleanup)**: Recursively dispose of nested reactive structures when the store is no longer needed.

<summary>Internal Mechanics</summary>

A regular object becomes a reactive store by wrapping its primitive properties in [signals](/reference/core/signal).

#### Store Architecture

Each store is a **reactive object** that converts object properties into reactive primitives.

```
Store Object
├── Property A → Signal<T>
├── Property B → Signal<T>
├── Readonly Property → Computed<T> (wraps Signal<T>)
└── Nested Store
    ├── Property C → Signal<T>
    └── Property D → Signal<T>
```

#### Property Transformation

When a store is created, the system transforms each property based on its type and characteristics.

- **Primitive values** (strings, numbers, booleans) become individual [signals](/reference/core/signal)
- **Objects** become nested stores with recursive property transformation
- **Arrays** become signals containing the array value
- **Functions** remain unchanged, preserving their original behavior

This transformation process occurs once during store creation, establishing a reactive structure that handles all subsequent updates.

#### Dependency Graph Integration

Store signals maintain their own set of dependencies and subscribers, propagating only through the specific paths that need updates.

```
Signal Property → Computed Values → Effects
       ↑                ↑              ↑
  (individual)    (property-specific)  (targeted)
```

This distributed approach eliminates the cascade re-computation problems common in monolithic state systems.

#### Reactive Property Binding

Store properties work with the templating engine's function reference binding system without extra configuration.

```jsx
// Direct reactive binding
const counter = store({
  count: 0,
  label: 'Count'
});

// Template binding
<h1>{counter.label}: {counter.count}</h1> // Automatically reactive
```

#### Update Propagation

Store updates follow the same efficient propagation mechanism as the core reactive system.

1. **Property Change** - A store property is updated via signal function call
2. **Dependency Marking** - Only computations dependent on that specific property are marked dirty
3. **Selective Propagation** - Changes propagate only through affected dependency chains
4. **Lazy Evaluation** - Computed values recalculate only when accessed AND dependencies changed
5. **Effect Execution** - Effects run immediately for properties they depend on

#### Memory Efficiency

The store system includes several memory optimization strategies.

- **Automatic Cleanup** - The cleanup system recursively disposes of all nested reactive values
- **Reference Management** - Circular references are prevented through careful property definition
- **Efficient Updates** - The `update()` function variant only applies changes that differ from the current state
